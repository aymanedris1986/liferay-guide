Client Extensions

How you add your own code to Liferay without putting it inside Liferay. Every CET type, what it hooks into, and a concrete use case for each.

In one sentence

A Client Extension (CET) is a unit of customisation declared in a client-extension.yaml and deployed as a zip or a container. It either injects assets into the browser, registers configuration, imports data, or exposes an HTTP endpoint Liferay calls — but it never runs inside Liferay's JVM.

Why this matters

Because CETs live outside the platform, they survive upgrades, work on SaaS, deploy independently, and can be written in any language. That is the whole reason to prefer them over OSGi modules.

What actually happens when you deploy one

It helps to know that the YAML is not what Liferay reads. The workspace Gradle plugin translates it:

client-extension.yaml │ createClientExtensionConfig (validates, classifies, checks grouping) ▼ <project>.client-extension-config.json one OSGi configuration per CET entry │ + static/ (frontend) batch/ (batch) site-initializer/ (siteInitializer) │ + Dockerfile + LCP.json (generated, except for microservices) ▼ <project>.zip the "LUFFA" (Liferay Universal File Format Archive) │ ├─ self-hosted: copied to bundles/osgi/client-extensions/ → file-install picks it up └─ SaaS: lcp deploy --extension <zip> → runs as its own container

So every CET type is, underneath, a configuration PID: a customElement becomes a CETConfiguration, an objectAction becomes a FunctionObjectActionExecutorImplConfiguration, and so on. That is why a CET can be "installed" and still do nothing: the configuration landed, but whatever it points at (a URL, a service address) is wrong.

Where frontend files are served from

On self-hosted, Liferay serves a frontend project's static/ folder itself, under /o/<project-name>/. That is why urls: - index.*.js works: the glob is resolved against the hashed file names at build time and prefixed with that base URL. On SaaS the same files are served by a small Caddy container the platform runs for you.

The four classifications

FRONTEND assets injected into the browser (CSS, JS, custom elements, themes) CONFIGURATION OAuth apps, typed settings, iframes (no code you host) MICROSERVICE an HTTP endpoint Liferay calls INBOUND (object actions, validators, workflow) BATCH bulk data import / whole-site setup (batch, siteInitializer)

The classification of each type is fixed by the workspace plugin (client-extension.properties in com.liferay.gradle.plugins.workspace). One surprise: iframe is classified as configuration, not frontend — it ships no files, only a URL.

Which types may share one project

This is enforced by the workspace Gradle plugin, and the failure appears late — after the assemble tasks have already printed success.

Allowed groupingCovers
any single classification on its owne.g. several globalCSS + customElement entries
configurationOAuth apps, instanceSettings, iframe
configuration + batchA batch or siteInitializer with its OAuth companion
configuration + frontendTheme, CSS, JS, custom elements, with OAuth if needed
configuration + microserviceHandlers with their OAuth app
batch, frontend and microservice can never be combined

Add a themeCSS to your siteInitializer project and the build fails at createClientExtensionConfig:

The combination of client extensions in [configuration, batch, frontend] cannot be
grouped in a single project.

A complete site is several sibling projects, not one. Expect at least: the initializer + its OAuth, a frontend project for theme/CSS, and a microservice project per handler group. A batch/siteInitializer project must also contain exactly one oAuthApplicationHeadlessServer and at most one batch/initializer entry — both are hard errors in the plugin.

Scope: the key that decides where CSS and JS actually appear

A globalCSS or globalJS with the default scope: layout does nothing on its own. It becomes available, and an administrator attaches it to a page, page set, or master page through the page's design settings. With scope: company it is injected automatically on every page of the instance, including the Control Panel and site administration. scriptLocation only has an effect for company-scoped JS. themeCSS has its own pair: layout (site pages) or controlPanel (the admin theme).

"I deployed my globalJS and nothing loads"

Nine times out of ten it is scope: layout with nobody having attached it to a page. Scope can only be set from YAML; a JS or CSS extension created through the UI is always page-scoped.

# customElement — a React widget
assemble:
    -   from: build/static
        into: static

badael-org-chart:
    cssURLs:
        - css/main.*.css
    friendlyURLMapping: badael-org-chart
    htmlElementName: badael-org-chart
    instanceable: false
    name: Badael Org Chart
    portletCategoryName: category.client-extensions
    type: customElement
    urls:
        - js/main.*.js
    useESM: true
Custom-element rules the validator enforces

htmlElementName must start with a lowercase letter, contain at least one hyphen, use only valid characters, and must not be a reserved name such as font-face or annotation-xml. That is the Web Components spec, not a Liferay whim. useESM: true loads your urls as type="module"; leave it false for a classic IIFE bundle.

For an iframe, instanceable cannot be changed after first deploy — the validator rejects the update. Decide up front.

hashify is how you get cache-busting for free

In assemble, hashify: global.css renames the file to global.<hash>.css; the url: global.*.css glob then resolves to the hashed name. Browsers can cache aggressively and still pick up every redeploy.

Microservice types

These expose an HTTP endpoint that Liferay calls inbound. Each entry requires oAuth2ApplicationExternalReferenceCode (pointing at an oAuthApplicationUserAgent companion that carries .serviceAddress and .serviceScheme) and its own resourcePath. Liferay concatenates them: <scheme>://<serviceAddress><resourcePath>.

Registering the CET only makes it selectable. You still attach it: pick the object action's "then" as your CET in the object's Actions tab, pick your validation rule type in Validations, reference the workflow action from the Kaleo definition. The allowedObjectDefinitionNames list only narrows where it may be chosen.

On self-hosted, the zip does not run your service

Deploying a microservice zip to osgi/client-extensions registers the configuration and the OAuth app. The Spring Boot / Node process itself is yours to run (blade gw bootRun locally, a container or VM in real environments) at the .serviceAddress you declared. On Liferay SaaS the same zip is deployed as a container and the platform runs it. "Deployed fine, every call times out" on self-hosted almost always means nothing is listening on that address.

The token flows both ways

Liferay calls your endpoint with a Bearer JWT issued for the oAuthApplicationUserAgent app on behalf of the user who triggered the event. Your service should validate it (the Liferay Spring Boot client-extension library does this for you), and can use it to call back into Liferay's Headless APIs — as that user, with their permissions, limited to the app's scopes. That is why the companion is a UserAgent app and not a server app.

Configuration types

TypePurpose
oAuthApplicationHeadlessServerService-account OAuth app (client credentials) — the CET calls into Liferay on its own initiative. Used by batch, siteInitializer, and scheduled jobs such as a cron microservice.
oAuthApplicationUserAgentUser-delegated OAuth app — Liferay calls out to the CET and passes a user's token. Used by microservice CETs.
instanceSettingsSets an OSGi configuration by pid, with the configuration's own fields as keys, as if an admin had filled in Instance Settings. Can be narrowed to a site with siteExternalReferenceCode.
iframeA widget that frames an external URL (url required). Classified as configuration, so it may ride along in any project.

The direction of the call is the whole distinction, and it is the single most common cause of a CET that deploys cleanly and authenticates against nothing. Both OAuth types require .serviceAddress, .serviceScheme and scopes.

# instanceSettings — configuration as code
badael-redirect-allowlist:
    allowedDomains:
        -   "*.badael.ae"
    name: Badael Redirect Allowlist
    pid: com.liferay.redirect.internal.configuration.RedirectURLConfiguration
    securityMode: domain
    type: instanceSettings

Finding the pid and field names: open the setting in Instance Settings, use Export from the kebab menu, and read the keys out of the exported .config file.

Batch types

TypePurpose
batchBulk data import through the Batch Engine: batch/*.batch-engine-data.json files with a configuration (className, parameters) + items envelope
siteInitializerA whole site from source: pages, fragments, objects, roles, content — see Site initializers. Requires siteName and siteExternalReferenceCode; optional membershipType, parentSiteKey.
// batch/01-departments.batch-engine-data.json
{
	"configuration": {
		"className": "com.liferay.object.rest.dto.v1_0.ObjectEntry",
		"parameters": {
			"createStrategy": "UPSERT",
			"importStrategy": "ON_ERROR_FAIL",
			"updateStrategy": "UPDATE"
		},
		"taskItemDelegateName": "C_Department"
	},
	"items": [
		{"externalReferenceCode": "dept-hr", "name": "Human Resources"},
		{"externalReferenceCode": "dept-it", "name": "Information Technology"}
	]
}

Give every item an externalReferenceCode and use UPSERT: then redeploying the batch is idempotent instead of creating duplicates. ON_ERROR_FAIL stops at the first bad item instead of importing half a file. For object entries, taskItemDelegateName (a sibling of parameters, not inside it) is how the engine knows which object the generic ObjectEntry class means.

There is no batch/ directory inside a site initializer

*.batch-engine-data.json files placed in an initializer tree are packaged into the zip and silently ignored. The build succeeds, the site provisions, no data appears. That envelope belongs to the separate batch CET type.

Building and deploying

cd client-extensions/<name>
blade gw deploy                     # build the zip and copy it to bundles/osgi/client-extensions
../gradlew clean build              # just build; zip lands in dist/ (use this for SaaS)
lcp deploy --extension dist/<name>.zip   # SaaS only

The assemble block says what gets packaged. Each entry is a copy: from a folder or fromTask a Gradle task's outputs (mutually exclusive), optionally filtered by include globs, placed into a folder of the zip, with optional hashify.

EnvironmentHow a CET gets thereWhat runs it
Self-hostedZip into [Liferay Home]/osgi/client-extensions/, or bundled via gradlew distBundleZipLiferay registers config and serves static files; you run microservices
SaaSlcp deploy --extensionEach zip becomes its own service in your Liferay Cloud project
PaaSCommit to the workspace's client-extensions/ and pushA separate client-extension build pipeline
BUILD SUCCESSFUL is not verification

Success means the zip was produced. Confirm the bundle reached STARTED in the log, and for an initializer confirm the Initializing <Site> count actually increased. Gradle's up-to-date check is content-based, so with no source edit a redeploy rewrites nothing at all.

Which virtual instance?

A deployed CET lands in the default virtual instance unless you target another one with the workspace Gradle property liferay.virtual.instance.id (the older dxp.lxc.liferay.com.virtualInstanceId is deprecated). On a multi-instance portal this explains the "it deployed but I can't see it" case.

Traps

Wrong OAuth type = silent auth failure

oAuthApplicationHeadlessServer for CETs that call into Liferay on their own; oAuthApplicationUserAgent for CETs Liferay calls. Getting it backwards deploys fine and fails at the first request.

401 vs 403

403 means the token is valid but its scopes do not cover the endpoint — add the scope and redeploy. 401 means the token itself is wrong — check the OAuth registration, not the scopes.

Scope names follow the JAX-RS application, and objects are per-object

A scope is <application name>.everything (or .everything.read/.write), where the name comes from the API module: Liferay.Headless.Admin.Site, Liferay.Object.Admin.REST (object definitions, /o/object-admin/…), and so on. Object entries (/o/c/<plural>) are different: every published object registers its own JAX-RS application, so its scope is named after that object. Copy the exact string from the scope picker in Control Panel → OAuth 2 Administration. Liferay.Headless.Object.everything is a real scope, but it belongs to /o/headless-object (object entry folders), not to /o/c/….

A src in scriptElementAttributes fails the build

The plugin rejects it: the script URL belongs in url. Attribute values must be scalars (async: true, data-senna-track: permanent).
