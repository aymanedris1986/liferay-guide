Web Content

The editor-owned content type. A Web Content article is a set of filled-in fields, versioned, translatable, and approvable — it carries no layout of its own.

In one sentence

A Web Content article (internally a Journal Article) is one record of editorial content: a title plus values for the fields its Content Structure defines, rendered by a Web Content Template and placed on a page.

Maintenance mode since 2026.Q1

Liferay moved classic Web Content (along with Documents & Media and Asset Libraries) into maintenance mode in 2026.Q1. It is fully supported and keeps getting fixes, but new features go to the object-based Liferay CMS, which is off by default on 2026.Q2 (see Two CMSes). Everything on this page still applies to Badael.

What it actually is

Three things are always involved, and confusing them is the #1 source of "why is my content blank":

Content Structure ──── defines what fields exist ────▶ "Title, Subtitle, Image, Body, Author" ▲ │ │ an article picks one structure │ filled in by an editor │ ▼ Web Content Article ───────────────────────────────▶ the actual values for one news item │ │ rendered by ▼ Web Content Template ──── FreeMarker markup ────▶ the HTML a visitor sees

The structure is the shape. The article is the data. The template is the look. You can swap the template without touching a single article, and that is the whole point of the split.

Basic vs structured

KindWhat it isUse when
Basic Web ContentAn article using the built-in Basic Web Content structure (key BASIC-WEB-CONTENT, in the Global site), which has one localizable rich-text field called contentFree-form prose: an "About us" blurb, a legal notice. Editors get a WYSIWYG and nothing to fill in wrong.
Structured Web ContentArticle bound to a Content Structure you designedAnything repeated with consistent parts: news, press releases, staff profiles, product cards. Enables reliable collections and display pages.

So there is no such thing as an article "without a structure". Every article has exactly one, chosen at creation and fixed afterwards. You can't move an existing article to another structure from the UI. "Basic" just means "the generic one-field structure".

Rule of thumb

If you will ever want to list these items, filter them, or give each one its own URL, it must be structured. Basic web content is a dead end for anything but a one-off block of prose.

What you get for free

  • Versioning — every save creates a version (1.0, 1.1, …). Editors can compare and restore.
  • Translation — per-locale values on each field, with a translation UI and a per-locale completion state.
  • Scheduling — display date, expiration date, review date.
  • Workflow — attach a Kaleo workflow so articles need approval before going live.
  • Asset behaviour — categories and tags, related assets, ratings, comments, and search indexing come along automatically.
  • Folders — for organisation and per-folder permissions/workflow.

Compare with an Object. Objects can also be localized (per field, 2023.Q3+), put through workflow, and tagged/categorized. What they don't have on 2026.Q2 classic is the editorial kit: compare/restore versions, display/expiration/review dates, preview-before-publish, and the side-by-side translation UI with XLIFF export. (Object entry versioning exists only with the new CMS feature flag. See the two-CMS note.) That kit is the real dividing line.

Identity: the IDs an article carries

An article has more than one identifier, and code that uses the wrong one breaks quietly:

IDWhat it isUse it for
articleIdHuman-readable key, unique per site (e.g. LEADERSHIP_PROFILE_8). The same across versionsWeb Content Display config, initializer tokens
resourcePrimKeyThe article's asset/resource ID, stable across versions. It is what the headless API returns as a structured content's idREST calls, asset links, permissions
id (row ID)One database row per version. It changes every time the article is savedNothing. Never store it
externalReferenceCodeYour own stable key, portable across environmentsSync scripts and anything that must match DEV to PROD

Versions and statuses

Each save creates a version row with a status: Draft, Pending (in workflow), Approved, Scheduled (approved, display date in the future), Expired. Visitors only ever see the latest approved version whose display date has passed. So "I edited it and nothing changed" usually means the edit is sitting as a draft or in a workflow task, and the site is still showing the previous approved version. That is working as designed.

How it connects to everything else

  • Content Structure — defines its fields
  • Web Content Template — renders it
  • Collections — list many articles
  • Display Page Template — one URL per article
  • Fragments — map article fields into page markup
  • Categories — what collections filter on
  • Workflow — approval before publish
  • Headless APIs — create and read articles
  • Permissions — per-article and per-folder VIEW/UPDATE

Reading articles over REST

In the Headless Delivery API an article is a structured content and a structure is a content structure. The useful endpoints:

# all articles in a site (title, dates, taxonomy, contentFields[])
GET /o/headless-delivery/v1.0/sites/{siteId}/structured-contents

# articles of ONE structure, filterable by a field value
GET /o/headless-delivery/v1.0/content-structures/{structureId}/structured-contents
    ?filter=contentFields/department eq 'Finance'

# one article, rendered through a given template (returns HTML)
GET /o/headless-delivery/v1.0/structured-contents/{id}/rendered-content/{templateId}

Filtering on contentFields/<fieldReference> only works on the per-structure endpoint, and only for fields indexed as keyword. The site-wide endpoint rejects that syntax, so use a search blueprint there. (Source: Liferay KB, "How to filter web content by structure field with headless APIs".)

In source control

A site initializer carries articles as a pair of files under journal-articles/: a .json with metadata and an .xml with the same base name holding the field values. This example is taken from Liferay's own teaser-showcase initializer:

journal-articles/leadership/leadership_profile_8.json
{
	"ddmStructureKey": "Leadership Profile",
	"folder": "Leadership",
	"name": "Nigel Cook"
}
journal-articles/leadership/leadership_profile_8.xml
<root available-locales="en_US" default-locale="en_US" version="1.0">
	<dynamic-element field-reference="name" index-type="keyword" name="name" type="text">
		<dynamic-content language-id="en_US"><![CDATA[Nigel Cook]]></dynamic-content>
	</dynamic-element>
	<dynamic-element field-reference="image" index-type="text" name="image" type="image">
		<dynamic-content language-id="en_US">
			<![CDATA[[$DOCUMENT_JSON:/site-initializer/documents/group/Leadership/leader.png$]]]>
		</dynamic-content>
	</dynamic-element>
</root>

Note the [$DOCUMENT_JSON:…$] token: media references resolve at provisioning time, so the XML never hardcodes an ID. Same idea as every other initializer token. The key is the document's path inside the initializer bundle.

What the importer (BundleSiteInitializer) actually reads from the .json tells you a few things you can't see from the sample:

KeyEffect
nameThe title, set for the site default locale only. Translated titles can't be seeded this way
ddmStructureKeyStructure key. For initializer structures this is the <name> in ddm-structures/*.xml. It is looked up in the site and its ancestors, so Global structures such as BASIC-WEB-CONTENT resolve too
ddmTemplateKeyOptional default template
articleIdOptional. Defaults to the file name, upper-cased (leadership_profile_8.json → LEADERSHIP_PROFILE_8)
assetCategoryERCs, assetTagNamesArrays of categories (by ERC) and tags
folderIgnored. The folder comes from the directory: journal-articles/leadership/ becomes a folder called leadership, unless a sibling leadership.metadata.json supplies name, description, externalReferenceCode, viewableBy

Each imported article also registers a [$JOURNAL_ARTICLE_ID:<ARTICLEID>$] token, which resolves to its resourcePrimKey, for later files to reference.

Reprovisioning overwrites editor changes

If an article with that articleId already exists, the initializer calls updateArticle with the XML from source. Every reprovision therefore creates a new version containing the seeded values and silently replaces whatever an editor typed on the live site. Keep seeds for content that source control owns (demo, legal boilerplate). Content that editors own should not be in journal-articles/ after the first provisioning.

Traps

Changing a structure after articles exist

Removing a field or changing its field reference on a live structure cuts every existing article off from the value stored under the old reference. Templates render empty and the editor form no longer shows it. Add fields freely. Removing or re-keying them is a migration, not an edit.

Guest cannot read what you can

A logged-out visitor needs VIEW on the article (and its folder) for it to render on a page. For headless reads, Guest also needs a Service Access Policy that allows the endpoint. Your article looks fine to you and returns nothing to them. Verify with an unauthenticated curl or a private window, never with your own session.

Basic content in a structured slot

A dynamic collection filtered to your News Article structure silently skips articles an editor created as Basic Web Content. They belong to the BASIC-WEB-CONTENT structure, so they don't match. The list just comes back shorter than expected, and because an article's structure can't be changed afterwards, the fix is to recreate them.

Expired and scheduled articles vanish without an error

An expiration date in the past, or a display date in the future, removes the article from collections, search, and Web Content Display for visitors. Admins still see it in the admin list, marked with a status label. When "one item is missing" from a list, check the dates before debugging the collection.
