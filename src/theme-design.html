Plus master pages, which control structure rather than style, and layout-set settings, which switch the stock theme chrome on and off.

Style books

A style book is a named set of frontend token values. The theme declares which tokens exist (a frontend token definition); the style book sets them; every page using that style book picks up the values without a deploy.

How the pieces fit

THEME (Classic, or a themeCSS CET) └── frontend-token-definition.json which tokens exist, their editor type, default, and the CSS variable each maps to │ ▼ STYLE BOOK (bound to that theme via themeId) └── frontend-tokens-values.json this site's values for those tokens │ ▼ :root { --brand-color-1: #0b5fff; --font-family-base: Tajawal, sans-serif; … } │ ▼ Clay/Bootstrap CSS + your fragment CSS read var(--…)

Style book files in an initializer

The values live in a separate file that style-book.json points to — StyleBookEntryZipProcessorImpl reads frontendTokensValuesPath, not an inline object:

style-books/badael-brand/style-book.json
{
	"defaultStyleBookEntry": true,
	"frontendTokensValuesPath": "frontend-tokens-values.json",
	"name": "Badael Brand",
	"themeId": "classic_WAR_classictheme",
	"thumbnailPath": "thumbnail.png"
}

style-books/badael-brand/frontend-tokens-values.json
{
	"brandColor1": { "cssVariableMapping": "brand-color-1", "value": "#0b5fff" },
	"fontFamilyBase": { "cssVariableMapping": "font-family-base", "value": "Tajawal, sans-serif" },
	"borderRadius": { "cssVariableMapping": "border-radius", "value": "8px" }
}

The keys (brandColor1, fontFamilyBase) are token names from the theme's frontend-token-definition.json; cssVariableMapping is the CSS variable without the leading --. Values may reference other tokens: "value": "var(--gray-900)".

Inline values and invented token names are silently ignored

An inline frontendTokensValues object in style-book.json is not read at all — the style book imports with no values and the site looks stock. A token name the theme does not define (Classic has no fontFamily1; it has fontFamilyBase, fontFamilySansSerif, fontFamilyMonospace) is likewise ignored. Copy names from the theme's definition, and after provisioning open the style book in the UI to check the values actually took.

Prefer style books for anything a designer will change

No deploy, no restart, editable in the UI, versionable in the tree, and it survives reprovisioning. It is the cheapest rung on the cost ladder for appearance.

Use the tokens in fragment CSS through the CSS custom properties they generate, so a token change restyles your fragments too:

.badael-hero {
	background: var(--brand-color-1);
	border-radius: var(--border-radius);
	font-family: var(--font-family-base);
	padding: var(--spacer-5);
}

Classic's token categories, for orientation: colour system (brand colours, grays, theme colours such as --primary), spacing (--spacer-0 … --spacer-10), general (body, borders, shadows), layout (container widths), typography (font families, sizes, weights, --h1-font-size … --h6-font-size), and buttons (--btn-primary-background-color and friends). If a design needs something outside that list, that is your signal for a themeCSS CET with its own token definition.

Which style book wins

A page can pick a style book explicitly; otherwise it inherits from its master page, and otherwise the site's default (defaultStyleBookEntry: true). A style book only makes sense for the theme whose tokens it sets, which is why it carries themeId.

themeCSS client extensions

The modern replacement for the legacy theme WAR. It ships compiled CSS — typically Clay variable overrides — and appears in the theme picker.

assemble:
    - from: build/buildTheme/css
      into: static

badael-home-theme-css:
    clayRTLURL: css/clay_rtl.css
    clayURL: css/clay.css
    frontendTokenDefinitionJSON: src/frontend-token-definition.json
    mainRTLURL: css/main_rtl.css
    mainURL: css/main.css
    name: Badael Home Theme CSS
    type: themeCSS

frontendTokenDefinitionJSON is optional and is what makes a themeCSS CET work with style books: it declares the tokens the CET's CSS reads, in the same format as Classic's definition. Each token has a name, a defaultValue, an editorType (ColorPicker, Length, …) and a mappings entry of {"type": "cssVariable", "value": "btn-border-radius"}. Without it, a style book edited while your CET is applied has nothing of yours to set.

The RTL URLs matter for Arabic-language sites: Liferay serves the RTL sheet when the locale direction is right-to-left, and omitting them means an LTR layout under Arabic.

A themeCSS CET cannot be selected from the initializer tree

Liferay attaches a theme through a ClientExtensionEntryRel on the layout, master layout, or layout set. BundleSiteInitializer has no handler that creates that relation, and there is no key in metadata.json for it either.

So a deployed themeCSS CET is available but not applied until someone picks it in Site Administration → Design → Theme — and that selection is lost on every reprovision.

Plan accordingly. Appearance that must survive delete-and-redeploy has to come from things the tree can express: a style book with defaultStyleBookEntry: true, the master page, fragment CSS, and layout-set settings. Reach for themeCSS for Clay-level overrides that have no token — Classic's headings tokens are sizes only (h1FontSize…h6FontSize); there is no heading font family, weight or colour token, for instance — and say plainly that applying it needs a manual step.

Layout set settings

Switching off stock theme chrome so your master page's header and footer do not render underneath the theme's:

layout-set/public/metadata.json
{
	"settings": {
		"lfr-theme:regular:show-footer": false,
		"lfr-theme:regular:show-header": false,
		"lfr-theme:regular:show-header-search": false
	},
	"themeName": "Classic"
}

What the 2026.Q2 layout-set handler actually reads: themeName (the theme's display name, matched exactly), settings (copied into the layout set's settings), and three optional sibling files — css.css (layout-set custom CSS), js.js (layout-set JavaScript) and logo.png (site logo). It does not read themeId or colorSchemeId; those keys are ignored.

Prefer this over CSS hiding

Hiding #banner / #footer with a globalCSS rule is instance-wide, and there is no site-specific body class to scope it to — so you would hide the chrome on every other site too. The setting is scoped to this layout set.

Legacy themes (WAR)

The old themes/ directory with FreeMarker templates (portal_normal.ftl), SCSS, and theme settings. Still supported, but:

Legacy theme WARModern equivalent
portal_normal.ftl header/footer markupMaster page template + fragments
SCSS variablesStyle book tokens
Theme CSSthemeCSS CET
Theme settingsStyle book + layout-set settings
Theme JSglobalJS CET

Do not start a new project on a theme WAR. It blocks SaaS and makes every upgrade a re-test. The same goes for the bundled alternatives: the Dialect theme is archived and removed from the default build in 2026.Q3 — Classic plus style books plus themeCSS is the supported path.

Accessibility — check these while you still can change them

  • Brand colour against its background must reach 4.5:1 for body text, 3:1 for large text. Check the token, not the screenshot.
  • Do not encode meaning in colour alone — a red "rejected" pill needs the word too.
  • Keep focus outlines. Removing them in fragment CSS is the most common accessibility regression in Liferay projects.
  • Heading levels follow document order; expose the level as a fragment configuration so editors can fix it without a deploy.
  • For Arabic, verify the RTL sheet actually loads — mirrored paddings and icons are what break first.

How it connects

  • Fragments — consume the tokens
  • Master pages — structure, not style
  • Pages — style books apply per page too
  • Client extensions — themeCSS, globalCSS, spritemap, favicon
  • Site initializers — what survives a reprovision

Traps

A frontend project cannot live in the initializer project

themeCSS is classified frontend; siteInitializer is batch. The workspace plugin forbids the combination. Sibling projects — see grouping rules.

A token in the wrong place does nothing, quietly

Style-book values arrive as CSS custom properties. Fragment CSS that hard-codes #0b5fff will never follow the brand; fragment CSS that redefines --brand-color-1 overrides the style book wherever that rule matches, and nobody editing the style book will know why. Read tokens in fragments, never write them.

A flat handler timing does not mean it failed

Adding layout-set/public/metadata.json leaves updateLayoutSets at 1 ms in the log even when the settings plainly took effect. For single-file handlers, assert the outcome — fetch the page and confirm the chrome is gone — rather than reading the timing.
