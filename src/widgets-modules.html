The vocabulary

TermMeans
PortletThe Java standard for a self-contained web component with its own request lifecycle
WidgetWhat Liferay calls a portlet in the UI — the things in the "Add" sidebar
OSGi moduleA JAR deployed into Liferay's JVM. May contain portlets, services, overrides, listeners
Service BuilderLiferay's code generator for persistence layers in a module
WARThe older packaging; themes and some legacy apps

Search is the one you should not rebuild

Search Bar + Search Results with facets is a large amount of functionality for zero code. Wire it to vocabularies for facets and style it with CSS before considering anything custom.

When a custom OSGi module is genuinely required

RequirementWhy a CET cannot do it
A custom InfoCollectionProviderThe interface is registered in the OSGi registry; there is no CET equivalent
A custom indexer or search post-processorRuns inside the search pipeline
A Model Listener reacting to core entities (User, Layout)Only Objects expose lifecycle hooks to CETs
Overriding a Liferay service implementationRequires being in the same OSGi registry
A custom authentication or auto-login verifierPart of the request pipeline
Service Builder persistence for complex Java domain logicObjects cover most of this; genuinely complex domains occasionally do not
A custom portlet with server-side render lifecycleCustom Elements render client-side

The real cost

Client ExtensionOSGi module
RunsOutside the JVM (or just in the browser)Inside Liferay's JVM
Works on SaaSYesNo
Upgrade impactMinimal — it talks to versioned REST APIsRe-compile and re-test against each release
A bug can take down the portalNoYes — same heap, same threads
LanguageAnythingJava
Deploy cadenceIndependentCoupled to the portal
Local buildblade gw deployblade gw deploy + bundle restart in many cases
The decision is mostly about SaaS and upgrades

One OSGi module in the estate means the whole system is self-hosted and every quarterly release is a regression cycle. That is sometimes the right call. It should never be an accidental one.

Workspace layout

modules/ OSGi modules and WARs (liferay.workspace.modules.dir) themes/ legacy theme WARs (liferay.workspace.themes.dir) client-extensions/ CETs ← start here configs/ per-environment properties: common, local, dev, uat, prod, docker bundles/ the Tomcat install + deployed artifacts (not in git)
blade gw deploy                       # build and deploy the current project
blade gw tasks                        # what is available
blade server start --tail             # start Tomcat and follow the log

Deployed artifacts land in bundles/osgi/modules and bundles/osgi/client-extensions; logs in bundles/tomcat*/logs/catalina.out and bundles/logs/liferay.<date>.log.

Success is STARTED in the log, not a green build

A module can build, deploy, and sit in INSTALLED or RESOLVED forever because of an unsatisfied dependency, with no error on the console you were watching.

How it connects

  • Client extensions — the default choice
  • Pages — where widgets are placed
  • ADTs — restyling widget output
  • Collection providers — a legitimate module use case
  • Objects — what replaced most Service Builder work
  • Themes — the WAR-to-CET migration

Decision, in order

  1. Can a built-in widget or collection do it? → done, no code.
  2. Can a fragment do it? → done, no deploy pipeline.
  3. Can an Object + object action do it? → done, no code.
  4. Can a CET do it? → done, and it survives upgrades.
  5. Only then: an OSGi module — and write down why, because the next person will ask.
