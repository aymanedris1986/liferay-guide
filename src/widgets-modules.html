The vocabulary

TermMeans
PortletThe Java standard for a self-contained web component with its own request lifecycle (render, action, resource phases)
WidgetWhat Liferay calls a portlet in the UI — the things in the "Add" sidebar. Custom-element and iframe CETs also show up here, registered as portlets.
OSGi moduleA JAR deployed into Liferay's JVM. May contain portlets, services, overrides, listeners
OSGi componentA class annotated @Component that the module registers in the service registry. This is how almost everything in Liferay is wired: you publish a service under an interface, and Liferay picks it up.
Service BuilderLiferay's code generator for persistence layers in a module
WARThe older packaging; themes and some legacy apps. Converted to an OSGi bundle on deploy.

When a custom OSGi module is genuinely required

The rule of thumb: if the requirement is "react to or change what Liferay does inside a request or transaction", and the thing you are hooking is not an Object, you are in module territory.

RequirementWhy a CET cannot do it
A custom InfoCollectionProviderThe interface is registered in the OSGi registry; there is no CET equivalent
A custom indexer contributor or search post-processorRuns inside the search pipeline
A Model Listener reacting to core entities (User, Layout)Only Objects expose lifecycle hooks to CETs
Overriding a Liferay service implementation (a service wrapper)Requires being in the same OSGi registry and the same transaction
A custom model resource permission — permission logic the role system cannot expressPermission checks run synchronously in-process
A custom authentication or auto-login verifierPart of the request pipeline
Service Builder persistence for complex Java domain logicObjects cover most of this; genuinely complex domains occasionally do not
A custom portlet with server-side render lifecycleCustom Elements render client-side
A real example from this project

Badael's one module, com.badael.intranet.content.permission, is an ObjectEntryLocalServiceWrapper plus a ModelResourcePermission registrar. It exists because the permission rule needs to run inside every object-entry permission check — something no object action or validation CET can do, because those run after the fact or only on save. That is what "genuinely required" looks like: narrow, written down, and not a UI.

The decision is mostly about SaaS and upgrades

One OSGi module in the estate means the whole system is self-hosted (or PaaS) and every quarterly release is a regression cycle. That is sometimes the right call. It should never be an accidental one.

What a portlet looks like in 2026.Q2

An MVC portlet is a class extending MVCPortlet, published as an OSGi component. Its "descriptor" is the component properties — there is no portlet.xml.

package com.badael.leave.web.internal.portlet;

import com.liferay.portal.kernel.portlet.bridges.mvc.MVCPortlet;

import jakarta.portlet.Portlet;

import org.osgi.service.component.annotations.Component;

@Component(
	property = {
		"com.liferay.portlet.display-category=category.badael",
		"jakarta.portlet.display-name=Leave Balance",
		"jakarta.portlet.init-param.view-template=/view.jsp",
		"jakarta.portlet.name=com_badael_leave_web_LeaveBalancePortlet",
		"jakarta.portlet.resource-bundle=content.Language",
		"jakarta.portlet.security-role-ref=power-user,user"
	},
	service = Portlet.class
)
public class LeaveBalancePortlet extends MVCPortlet {
}

Beyond the trivial case you split logic into separate components — MVCRenderCommand, MVCActionCommand, MVCResourceCommand — each registered with jakarta.portlet.name pointing at the portlet and an mvc.command.name. That keeps the portlet class empty and each command independently testable.

It is jakarta.portlet now, not javax.portlet

This DXP line runs on Jakarta EE: the portal ships com.liferay.jakarta.portlet-api, and its own portlets are registered with jakarta.portlet.name, jakarta.portlet.display-name and friends. Code, JSP imports, and component property names copied from older tutorials (javax.portlet.*, javax.servlet.*) need migrating. A module that still imports javax.portlet typically sits in INSTALLED with an unresolved package requirement.

Service Builder, briefly

Service Builder generates a persistence layer, local and remote services, and model classes from a service.xml. It produces two modules: *-api (interfaces, exported) and *-service (implementation, private).

blade create -t service-builder -p com.badael.leave badael-leave
# edit badael-leave-service/service.xml, then:
cd modules/badael-leave && blade gw buildService
blade gw deploy

You write business logic only in the generated *LocalServiceImpl; everything else is regenerated on each buildService. Upgrade steps for schema changes are your job (an UpgradeStepRegistrator).

Before reaching for Service Builder, check Objects

Objects give you tables, a REST and GraphQL API, permissions, workflow, and admin UI, with no code and no upgrade process. Service Builder wins only when you need real Java domain logic in the same transaction, complex queries Objects cannot express, or an existing SB codebase. A new SB entity on a SaaS-bound project is a contradiction.

Workspace layout

modules/ OSGi modules and WARs (liferay.workspace.modules.dir) themes/ legacy theme WARs (liferay.workspace.themes.dir) client-extensions/ CETs ← start here configs/ per-environment properties: common, local, dev, uat, prod, docker bundles/ the Tomcat install + deployed artifacts (not in git) gradle.properties liferay.workspace.product=dxp-2026.q2.11 ← the DXP version everything compiles against
blade init -v dxp-2026.q2.11 badael       # new workspace pinned to a product
blade gw initBundle                       # download/unpack the bundle into bundles/
blade create -t mvc-portlet -p com.badael.leave.web -c LeaveBalancePortlet badael-leave-web
blade gw deploy                           # build and deploy the current project
blade gw tasks                            # what is available
blade server start --tail                 # start Tomcat and follow the log
blade sh lb | grep badael                 # Gogo shell: list bundles and their state

Modules compile against release.dxp.api (declared compileOnly with no version — the workspace product supplies it), so bumping liferay.workspace.product is how you move every module to a new quarterly release in one place. Deployed artifacts land in bundles/osgi/modules and bundles/osgi/client-extensions; logs in bundles/tomcat/logs/catalina.out and bundles/logs/liferay.<date>.log.

Success is STARTED in the log, not a green build

A module can build, deploy, and sit in INSTALLED or RESOLVED forever because of an unsatisfied dependency, with no error on the console you were watching. In the Gogo shell, diag <bundle-id> names the missing package; scr:info <component> tells you why a component that is in a started bundle is still not active (usually an unsatisfied @Reference).

How it connects

  • Client extensions — the default choice
  • Pages — where widgets are placed
  • ADTs — restyling widget output
  • Collection providers — a legitimate module use case
  • Objects — what replaced most Service Builder work
  • Permissions — where a custom permission module plugs in
  • Themes — the WAR-to-CET migration

Decision, in order

  1. Can a built-in widget or collection do it? → done, no code.
  2. Can a fragment do it? → done, no deploy pipeline.
  3. Can an Object + object action do it? → done, no code.
  4. Can a CET do it? → done, and it survives upgrades.
  5. Only then: an OSGi module — and write down why, because the next person will ask.
A new React portlet is almost always the wrong shape

If the reason for a module is "I need a React UI as a widget", that is exactly what a customElement CET is for. It gets you the widget, the page placement and the configuration, without the JVM.
