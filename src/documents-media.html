In one sentence

Documents & Media is Liferay's file repository. It gives you folders of files with versioning, check-out, previews, categories, permissions and a stable URL. Just as important, a document is a reference: other content points at it instead of copying it.

Why it is not just a file upload

Where files live: sites vs asset libraries

A Documents and Media library belongs to a scope, which is either a site or an Asset Library (DXP). An asset library is a site-less content repository that you connect to one or more sites. Its files, document types and vocabularies become selectable from those sites. When the same brand PDFs or logos are needed across Badael's sites, the asset library is the answer, not duplicating the files in every site.

Asset Library "Badael Shared" Site "Badael Intranet" ├── Documents: logos/, policies/ ◀── connected ── picker, collections, fragments ├── Document Types: Policy can select library files └── Vocabularies: Department ◀── connected ── Site "Badael Public"

The binary itself is stored by the configured file store: the file system (the default), a database store, or S3/GCS/Azure-style stores. The database holds only the metadata row. This matters for backups: a DB dump alone does not give you back your documents.

Document types are created under Documents and Media → Document Types in a site or asset library. Every custom type keeps the four default fields, and yours appear in addition to them. Since 7.4 the type is built with the same Data Engine form builder as content structures, so fields behave the same way (Field References, repeatable fields, field sets).

The common intranet question

Take "Policy documents with an owner, a department, and a review date". Is that a Document Type, or an Object with an attachment field?

Use a Document Type when the file is the thing and the fields describe it. Use an Object when the record is the thing, it has a lifecycle or relationships, and the file is one attribute of it. If there's an approval flow, a status, or a link to another record, go with an Object.

How documents get referenced

FromHow
A structure Image or Document fieldStores a reference; replacing the document updates every article
A fragment editabledata-lfr-editable-type="image" opens the media picker
An object Attachment fieldStores a file entry reference
A site initializer[$DOCUMENT_JSON:/site-initializer/documents/group/<folder>/<file>$] for Image/Document field values. [$DOCUMENT_URL:…$] and [$DOCUMENT_FILE_ENTRY_ID:…$] also exist when you need just the URL or ID
A direct URL/documents/d/<site-friendly-url>/<file-friendly-url>. The older /documents/<groupId>/<folderId>/<title>/<uuid> form still resolves

A site initializer's files go under documents/group/, where the folder tree becomes the D&M folder tree. Files for the company-wide Global scope go under documents/company/. The DOCUMENT_JSON token expands to a serialised file entry (IDs, UUID, group, plus an empty alt), which is the JSON an Image field value expects. Pasting a URL there does not work.

Reference, never copy

If you paste a document's URL as text into a Rich Text field, the reference is lost. Move or rename the file and the link 404s, and nothing warns you. Use the Image/Document field type or the media picker so Liferay tracks the relationship.

Listing documents

Documents are assets, so a dynamic collection can select them, filtered by folder, document type, or category. A fragment then renders each row. That's how you build "Policies & Manuals" pages without writing a file browser.

Documents folder "Policies" │ typed as Document Type "Policy" (owner, department, effective date) │ categorised under vocabulary "Department" ▼ Dynamic collection: type = Document, subtype = Policy, category = HR ▼ Collection Display + policy-row fragment ──▶ page /policies

In the row fragment, map editables to the document's fields: title, the download URL, and the document type's metadata fields, which show up as mappable fields once the collection is filtered to that subtype. Documents can also have a display page template of their own, bound to FileEntry and optionally a document type, which gives each file a landing page instead of a bare download.

How it connects

  • Content Structures — Image and Document fields
  • Fragments — image editables
  • Collections — document listings
  • Categories — how documents get filtered
  • Objects — attachment fields
  • Permissions — per folder and per file
  • Display page templates — a page per document
  • Headless APIs — upload and fetch

API

POST /o/headless-delivery/v1.0/sites/{siteId}/documents                 # multipart upload
POST /o/headless-delivery/v1.0/document-folders/{folderId}/documents     # into a folder
POST /o/headless-delivery/v1.0/asset-libraries/{assetLibraryId}/documents
GET  /o/headless-delivery/v1.0/documents/{documentId}

An upload is multipart/form-data with a file part and an optional document part. The document part is JSON carrying title, taxonomyCategoryIds, documentType and so on:

curl -u test@liferay.com:test \
	-F "file=@hr-leave-policy.pdf" \
	-F 'document={"title":"Leave Policy","taxonomyCategoryIds":[43120]}' \
	http://localhost:8080/o/headless-delivery/v1.0/sites/20121/documents

In this module, {siteId} is the site's group ID (or its site key). It is not the ERC path parameter that headless-admin-site uses.

Where Documents & Media is heading

Maintenance mode since 2026.Q1

Liferay's 2026.Q1 deprecation notes move Documents and Media, Web Content, Blogs, Knowledge Base and Asset Libraries into maintenance mode, with "consider using the Liferay CMS" as the replacement. The new CMS keeps files as file entries with customisable file structures, organised in spaces in place of asset libraries. It sits behind the CMS feature flag in 2026.Q2 and is GA without a flag from 2026.Q3. On a 2026.Q2 project, classic D&M is still the supported, fully integrated choice. Just don't build a long-lived custom extension on its internals, and keep your file handling behind the Headless APIs so a later move is a data migration rather than a rewrite.

Traps

Guest needs VIEW on the folder too

A public page that embeds a private document shows a broken image or gives a 403 on download, while the page itself returns 200. By default, the permission check on a file also checks VIEW on its parent folders. Grant VIEW on the folder chain, and verify with an unauthenticated curl. See Guest access.

Previews quietly missing

Uploads succeed, but PDFs and Office files show a generic icon. The external converters aren't installed or enabled (Control Panel → Server Administration → External Services). In Docker images, that is a container-level dependency, not a Liferay setting.

Removing a Document Type field orphans its metadata

This is the same rule as for content structures. Values are stored keyed by field, so deleting the field makes them unreachable.

Upload size has two limits

D&M's own maximum file size and the portal-wide upload request size both apply. A large video that fails to upload usually hits whichever limit is lower. Check both before blaming the proxy (which is the third limit).
