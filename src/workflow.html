Object actions

Logic attached to an Object, fired by a trigger.

TriggerFiresTypical use
onAfterAddAfter create, committedWelcome notification, audit entry
onAfterUpdateAfter update, committedStatus-change notification, recalculation
onAfterDeleteAfter deleteCascade cleanup, audit
standaloneOnly when invoked from the Actions menu or APIManual approve, export

The 2026.Q2 source defines a few narrower triggers too — onAfterAttachmentDownload, onAfterLogin, and onAfterRootUpdate (for the feature-flagged root-object hierarchies). Treat them as specialised and check the trigger dropdown for your object before relying on one. A standalone action is callable over REST, which is how an "Approve" button on a page runs it:

PUT /o/c/policyrequests/{id}/object-actions/{actionName}

A conditionExpression limits when it runs; empty means always:

requestStatus == "approved"
amount > 1000
(priority == "high") AND (assigneeId != null)

Actions run after the commit, and failures do not undo the save

Every onAfter* trigger fires once the entry is already stored. If the webhook times out or the CET throws, the entry stays; the failure shows up in the logs, not to the user. So never use an action as a gate — that is what validations are for — and make receivers idempotent, because a re-save delivers the same kind of event again.

Groovy actions are off by default — plan without them

Beyond being unavailable on SaaS, creating one is gated at runtime by ScriptManagementConfiguration, which has been off by default since 2024.Q3 (System Settings → Script Management). The definition is rejected outright:

400 ObjectActionExecutorKeyException
Groovy script based object actions are not allowed

Turning it on is a portal-wide decision to permit arbitrary script execution — surface it, never enable it quietly. Probe with a throwaway action before designing a solution around Groovy, and prefer a scriptless alternative: an Aggregation field replaces a hand-maintained counter outright.

If it is enabled: the bindings are the entry's fields as top-level variables, not an objectEntry object. A Registration field is bare attendeeName; a relationship FK is bare r_eventRegistrations_c_eventId. Also bound: creator, currentDate, currentUserId, groupId, id, entryDTO. Guard optional fields with binding.hasVariable("name").

Kaleo workflows

Kaleo is the approval engine. A workflow definition is XML describing states, tasks (assigned to roles or users), and transitions between them. Attach a definition to a content type — Web Content, an Object, Documents — in Process Builder → Configuration (instance-wide) or in a site's workflow settings, and new items enter the flow instead of publishing immediately.

Out of the box exactly one definition is installed: Single Approver. It is the best XML example you have, so here is its shape:

created ──review──▶ [ review task ]──approve──▶ approved (status → approved) (initial) │ ▲ reject resubmit ▼ │ [ update task ] assigned back to the author; status → denied, then pending
<task>
	<name>review</name>
	<actions>
		<notification>
			<name>Review Notification</name>
			<template><![CDATA[${userName} sent you a ${entryType} for review in the workflow.]]></template>
			<template-language>freemarker</template-language>
			<notification-type>email</notification-type>
			<notification-type>user-notification</notification-type>
			<recipients receptionType="to"><assignees /></recipients>
			<execution-type>onAssignment</execution-type>
		</notification>
	</actions>
	<assignments>
		<roles>
			<role><role-type>site</role-type><name>Site Content Reviewer</name></role>
			<role><role-type>regular</role-type><name>Portal Content Reviewer</name></role>
		</roles>
	</assignments>
	<transitions>
		<transition><name>approve</name><target>approved</target><default>true</default></transition>
		<transition><name>reject</name><target>update</target><default>false</default></transition>
	</transitions>
</task>

(Abridged: the real definition assigns review to a longer list of administrator, owner and reviewer roles across the regular, site, organization, asset library (depot) and account role types.) The approved state sets the entry's status with an action whose <status> is a WorkflowConstants integer: 0 approved, 1 pending, 2 draft, 4 denied.

ConceptMeaning
StateA resting point. Exactly one is <initial>; a state with no outgoing transition ends the flow
TaskWork assigned to a human; appears in their My Workflow Tasks. Tasks can carry timers (escalate or reassign after a delay)
ConditionA scripted branch: the script picks the transition to take
Fork / JoinParallel review ("legal and finance"); a join waits for all branches, a join-xor for the first
TransitionThe edge between nodes; its name is what a reviewer clicks and what the API sends
ActionScript or CET executed onEntry, onAssignment or onExit of a node
NotificationA message sent at a node — not the same thing as a notification template

Scripts in workflow are off by default too

Condition nodes, scripted assignments and script actions are Groovy. As of 2024.Q3 scripting is disabled by default — the same switch that blocks Groovy object actions — and Groovy is not available on SaaS. So a definition that branches on a condition node needs that decision made first. Scriptless alternatives: separate definitions per case, resource-action assignments, or a workflowAction CET that decides and transitions the task itself.

Designer or XML

The drag-and-drop Workflow Designer in Process Builder is a subscription (DXP) feature; its Source view edits the same XML. On Liferay Portal CE you write the XML and upload it. Either way, keep the XML in source control: it is the definition, the designer is only an editor for it. Publishing a changed definition creates a new version, and items already in flight carry on under the version they started with.

Status and visibility

Entries under workflow carry a status; a collection only shows approved items, which is usually what you want and occasionally the reason your list is empty.

A workflowAction CET receives the task with a transitionURL and advances it:

POST {transitionURL}   {"transitionName": "approve"}
Authorization: Bearer <token issued to the CET's OAuth2 application>

That is what Liferay's own Spring Boot sample (WorkflowAction1RestController) does. The transition name must be one leaving the current task.

Notification templates

The body of an email or in-app notification, managed in the Notifications app and over REST, with [%TERM%] interpolation:

POST /o/notification/v1.0/notification-templates

Hello [%POLICYREQUEST_AUTHOR_FIRST_NAME%],
Your request [%POLICYREQUEST_REQUESTID%] is now [%POLICYREQUEST_REQUESTSTATUS%].
Handled by [%CURRENT_USER_FIRST_NAME%] on [%CURRENT_DATE%].

Object field terms are [%<OBJECTNAME>_<FIELDNAME>%], both upper-cased (PolicyRequest.requestStatus → [%POLICYREQUEST_REQUESTSTATUS%]). The entry's author is [%<OBJECTNAME>_AUTHOR_FIRST_NAME%] and friends; the user who triggered the action is [%CURRENT_USER_…%]. The template editor lists every valid term for the chosen object — copy from there rather than guessing, because a misspelt term is not an error.

ChannelHow
EmailBuilt in — template type Email
In-app (the bell)Built in — template type User Notification
SMS, push, Teams, SlacknotificationType CET

Create the template first, then reference its ID from a notification object action. Templates live in an initializer under notification-templates/, and the action that uses one under object-actions/.

Workflow notifications are a different thing

Two unrelated systems send messages, and they are easy to confuse:

Kaleo workflow notificationNotification template
Lives inThe workflow definition XML, inside a node's <actions>The Notifications app / /o/notification
Fired byEntering, being assigned, or leaving a workflow nodeA notification object action
SyntaxFreeMarker, Velocity or plain text: ${userName}, ${entryType}, ${taskComments}[%TERM%] tokens
Recipients<assignees/>, the creator (<user/>), roles, scripted recipientsConfigured on the template
Channelsemail, user-notificationEmail, user notification, or a notificationType CET

Rule of thumb: messages about the review ("you have a task", "your submission was rejected") belong in the workflow XML. Messages about the data ("your request is now approved") belong in an object action plus a template, because they should fire however the data changed.

How it connects

  • Objects — what actions attach to
  • Forms — what triggers most flows
  • Web Content — the classic workflow target
  • Microservice CETs — where real logic lives
  • Roles — who gets the tasks
  • Notification templates in the template family
  • Collections — only approved items appear

A worked example

"Employee submits a policy exception; HR approves; requester is emailed; approved exceptions appear on the intranet."

  1. Object PolicyException with a state picklist field defaulting to submitted.
  2. A Form Container on a page creates entries.
  3. A Kaleo workflow attached to the object routes new entries to the HR role.
  4. An onAfterUpdate object action with condition exceptionStatus == "approved" fires a notification action using an email template. (Keep that picklist in step with the workflow: the workflow's own status and your state field are separate, so either the reviewer sets the picklist or a workflowAction CET updates it on approval.)
  5. A dynamic collection filtered to approved entries renders the intranet list; Guest needs a company-scope VIEW grant for it to be non-empty.

Nothing in that list requires custom code. Reach for a CET only at step 4, and only if the notification has to leave Liferay.

Traps

onAfterUpdate fires on every update

Including the one your own action just made. Always constrain with a conditionExpression, or an action that updates the same object will loop.

Workflow silently hides content

Attaching a workflow to a type that already had published items is fine, but every new item now sits in PENDING until someone approves it. Listings render short and nobody gets an error.

Nobody holds the assigned role

A task assigned to a site role that has no members in that site is a task nobody sees. The item sits pending forever. After deploying a definition, check that every assigned role has at least one real user in the relevant scope.
