Object actions

Logic attached to an Object, fired by a trigger.

TriggerFiresTypical use
onAfterAddAfter create, committedWelcome notification, audit entry
onAfterUpdateAfter update, committedStatus-change notification, recalculation
onAfterDeleteAfter deleteCascade cleanup, audit
standaloneOnly when invoked from the Actions menu or APIManual approve, export

A conditionExpression limits when it runs; empty means always:

requestStatus == "approved"
amount > 1000
(priority == "high") AND (assigneeId != null)

Groovy actions are off by default — plan without them

Beyond being unavailable on SaaS, creating one is gated at runtime by ScriptManagementConfiguration, which is off by default on current DXP. The definition is rejected outright:

400 ObjectActionExecutorKeyException
Groovy script based object actions are not allowed

Turning it on is a portal-wide decision to permit arbitrary script execution — surface it, never enable it quietly. Probe with a throwaway action before designing a solution around Groovy, and prefer a scriptless alternative: an Aggregation field replaces a hand-maintained counter outright.

If it is enabled: the bindings are the entry's fields as top-level variables, not an objectEntry object. A Registration field is bare attendeeName; a relationship FK is bare r_eventRegistrations_c_eventId. Also bound: creator, currentDate, currentUserId, groupId, id, entryDTO. Guard optional fields with binding.hasVariable("name").

Kaleo workflows

Kaleo is the approval engine. A workflow definition is XML describing states, tasks (assigned to roles or users), and transitions between them. Attach a definition to a content type — Web Content, an Object, Documents — and new items enter the flow instead of publishing immediately.

submit ──▶ [ review task ]──approve──▶ [ manager task ]──approve──▶ APPROVED (visible) │ │ reject reject ▼ ▼ PENDING (back to author) DENIED
ConceptMeaning
StateA resting point: created, approved, denied
TaskWork assigned to a human; appears in their My Workflow Tasks
TransitionThe edge between nodes
ActionScript or CET executed at a node
AssignmentRole, user, scripted assignee, or resource creator

Entries under workflow carry a status; a collection only shows approved items, which is usually what you want and occasionally the reason your list is empty.

A workflowAction CET receives the task with a transitionURL and advances it:

PATCH {transitionURL}   {"transitionName": "approve"}

Notification templates

The body of an email or in-app notification, with token interpolation:

POST /o/notification/v1.0/notification-templates

Hello [%USER_FIRST_NAME%],
Your request [%OBJECT_FIELD_requestId%] is now [%OBJECT_FIELD_requestStatus%].
ChannelHow
EmailBuilt in — template type Email
In-app (the bell)Built in — template type User Notification
SMS, push, Teams, SlacknotificationType CET

Create the template first, then reference its ID from a notification object action. Templates live in an initializer under notification-templates/, and the action that uses one under object-actions/.

How it connects

  • Objects — what actions attach to
  • Forms — what triggers most flows
  • Web Content — the classic workflow target
  • Microservice CETs — where real logic lives
  • Roles — who gets the tasks
  • Notification templates in the template family
  • Collections — only approved items appear

A worked example

"Employee submits a policy exception; HR approves; requester is emailed; approved exceptions appear on the intranet."

  1. Object PolicyException with a state picklist field defaulting to submitted.
  2. A Form Container on a page creates entries.
  3. A Kaleo workflow attached to the object routes new entries to the HR role.
  4. An onAfterUpdate object action with condition exceptionStatus == "approved" fires a notification action using an email template.
  5. A dynamic collection filtered to approved entries renders the intranet list; Guest needs a company-scope VIEW grant for it to be non-empty.

Nothing in that list requires custom code. Reach for a CET only at step 4, and only if the notification has to leave Liferay.

Traps

onAfterUpdate fires on every update

Including the one your own action just made. Always constrain with a conditionExpression, or an action that updates the same object will loop.

Workflow silently hides content

Attaching a workflow to a type that already had published items is fine, but every new item now sits in PENDING until someone approves it. Listings render short and nobody gets an error.
