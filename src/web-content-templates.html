In one sentence

A Web Content Template is a FreeMarker script attached to a Content Structure. It receives the field values of one article and outputs HTML.

What it actually is

Liferay hands your template variables named after the structure's fields. You write ordinary HTML with FreeMarker directives around it. The output is rendered on the server and cached — no JavaScript, no client round-trip, and it works for search engines and for visitors with JS disabled.

<article class="news-card">
	<h3>${headline.getData()}</h3>

	<#if summary.getData()?has_content>
		<p>${summary.getData()}</p>
	</#if>

	<#if heroImage.getData()?has_content>
		<img alt="" src="${heroImage.getData()}">
	</#if>
</article>

Repeatable fields and field sets become lists you iterate:

<ul>
	<#list links.getSiblings() as link>
		<li><a href="${link.url.getData()}">${link.label.getData()}</a></li>
	</#list>
</ul>

The template family — don't confuse these

FreeMarker shows up in four places that look alike and are scoped differently:

KindRendersAttached to
Web Content TemplateOne article's fieldsA Content Structure
Application Display Template (ADT)A widget's list output — Asset Publisher, Documents, Categories Navigation, BreadcrumbA widget type
Fragment (FreeMarker)A page building blockA fragment, with configuration.* in scope
Notification templateAn email or notification bodyA notification, using [%TOKEN%] syntax, not FreeMarker

All of these and the page-layout ones are laid out side by side on All template types.

When to use a template vs a fragment

Use a Web Content Template whenUse a Fragment when
The markup belongs to the content type — every news article should look like this everywhereThe markup belongs to the page — this hero looks like this on this layout
You need loops and conditionals over repeatable fieldsYou want editors to drag, drop, configure, and edit in place
The output is reused by widgets and display pages alikeYou need per-placement configuration options
You want zero page-editor involvementYou want the page editor to own the composition
They compose

The common pattern is both: a Collection Display fragment renders the list, and each item is rendered by the structure's card template. The fragment owns the grid; the template owns the card.

How it connects

  • Content Structure — supplies the fields
  • Web Content — the data rendered
  • Collections — where card templates get used
  • Display Page Templates — where full templates get used
  • Fragments — the page-level alternative
  • All template types — the disambiguation table

Traps

serviceLocator is usually off

Templates that reach into OSGi services via serviceLocator are blocked by default on current DXP, for the same reason Groovy object actions are: enabling it permits arbitrary code execution from the content editor. Prefer restClient or a CET. Design for it being off.

A missing field throws, it does not blank

Referencing a field the structure does not define raises a FreeMarker error and the whole block fails to render. Guard optional fields with ?has_content, and after any structure change re-check every template bound to it.

Templates are per-structure, and that binding is by key

Both the structure and the template are referenced by key (ddmStructureKey, ddmTemplateKey) in initializer files and API payloads. Renaming the display name is safe; changing the key breaks the link with no error at build time.

Escaping

${field.getData()} on a Rich Text field emits raw HTML by design. On a Text field that an editor controls, that is an injection surface — use ?html when the value should be treated as text.
