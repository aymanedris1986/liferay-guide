The asset framework

Web Content articles, Documents, Blog posts, Object entries and more are all assets. Every asset has one row in a shared AssetEntry table, next to its own table. Through that row it gets categories and tags, search indexing, related assets and view counts, and becomes eligible for a collection. Ratings and comments hang off the same framework where the type supports them.

This is why a single dynamic collection can list "everything tagged onboarding" across articles, PDFs and records at once. The collection queries the asset layer, not the three underlying tables.

JournalArticle ─┐ DLFileEntry ─┼──▶ AssetEntry ──▶ AssetCategory (in a vocabulary) BlogsEntry ─┤ │ └──▶ AssetTag (flat) ObjectEntry ─┘ └──▶ search index · related assets · collections

Practical rule

If a collection, a navigation structure, a search facet or any code depends on it, it must be a category. Tags help search relevance, and nothing you build logic on.

Vocabularies

A vocabulary is a named set of categories, and it is where governance lives. You create one under Site Menu → Categorization → Categories → New Vocabulary.

  • Scope: a site, an asset library, or the Global site. Global vocabularies can be used in every site of the instance, but they can only be edited in the Global site.
  • Associated asset types: limit a vocabulary to specific asset types, down to subtypes such as a particular structure or document type. That way "Department" only appears on the content it belongs to. The default is All Asset Types.
  • Required: set per associated asset type. For example, Policy documents must have a Department but news articles need not. Authors can't save that type without choosing a category.
  • Allow multiple categories: on by default. Turn it off for single-valued concepts like "owning department".
  • Visibility: Public categories can be used by visitors, in search facets and navigation. Internal ones are for editors' organising and searching only. You can't change this after saving.
  • Translatable: category names have per-locale labels, so an Arabic visitor sees Arabic facets.
Vocabulary "Department" (Global, required on Document > Policy, single-valued) ├── Human Resources ├── Finance │ ├── Accounts Payable │ └── Treasury └── Operations Vocabulary "Audience" (Internal visibility) ├── All staff └── Managers only

In a site initializer

Vocabularies are one JSON file each. A folder with the same name holds that vocabulary's categories, and nesting folders nests categories. Use group/ for the site and company/ for the Global site:

site-initializer/taxonomy-vocabularies/
	company/
		department.json               { "externalReferenceCode": "DEPARTMENT", "name": "Department", "viewableBy": "Anyone" }
		department/
			finance.json              { "externalReferenceCode": "DEPT-FINANCE", "name": "Finance", ... }
			finance/
				treasury.json
	group/
		audience.json

Other files refer to a category by its resource path, not its name: [$TAXONOMY_CATEGORY_ID:/site-initializer/taxonomy-vocabularies/company/department/finance.json$]. A vocabulary is referenced by name: [$TAXONOMY_VOCABULARY_ID:Department$]. Always set externalReferenceCode. With an ERC, re-provisioning updates the vocabulary in place. Without one, the initializer matches by name.

Design it before you create content

Retro-fitting a vocabulary onto 4,000 existing documents means someone has to categorise 4,000 documents. Decide the vocabularies at the start of the project, restrict them to the right asset types, and mark them required. It's a fifteen-minute decision that saves a week.

DoDon't
Few vocabularies, each answering one clear question ("which department owns this?")One giant "Tags" vocabulary that means nothing
Global (or asset-library) scope for cross-site conceptsDuplicating "Department" per site and hoping the names match
Restrict to asset typesShowing every vocabulary on every form and training editors to ignore them
Decide Public vs Internal deliberately, since it's permanentLeaving the default and discovering internal labels in a public facet
Translate category namesEnglish-only facets on a bilingual intranet
Reference categories by ERC in code and payloadsHard-coding numeric category IDs, which differ per environment

Traps

Site-scoped vocabularies do not cross sites

A collection on Site A can't filter by a category defined only on Site B. If content is shared, put the vocabulary in the Global site or in an asset library connected to both. Moving it later means re-categorising.

Deleting a category silently un-filters content

Items lose the association and drop out of every dynamic collection that filtered on it. The pages still render, just with fewer items.

Numeric IDs are per environment

Category 43120 on your laptop is a different number on UAT. A collection, fragment configuration or API call that hard-codes it passes review and fails after deployment. Resolve it by ERC, or through the initializer token.

Tags are typo magnets

onboarding, on-boarding and onboard are three different tags, and case handling is not something to rely on either. Anything load-bearing belongs in a vocabulary.

In the new Liferay CMS

The object-based Liferay CMS (behind the CMS flag in 2026.Q2, GA in 2026.Q3) keeps categories and tags. You can scope categories to a single space or share them across spaces. The modelling advice above carries over unchanged.
