The three pieces

SEGMENT "Managers" · "Arabic speakers" · "New joiners (< 90 days)" │ who the visitor is ▼ EXPERIENCE a whole alternative composition of ONE page, bound to a segment │ what they see ▼ A/B TEST two variants of an experience, measured against a goal which one performs better

Segments

A segment is a saved audience definition, evaluated per request. Criteria come from several sources:

SourceExamples
User attributesJob title, organization, user group, role, email domain
Organization / accountDepartment, region, B2B account membership
SessionLocale, browser, device, referrer, signed-in state
Behaviour (with Analytics Cloud)Pages viewed, content interacted with, campaign source
Custom fieldsAnything you added to the user model

Segments are reusable: define "Managers" once and use it for page experiences, personalised content, and notification targeting.

Segment vs role — they are not the same thing

A role answers "what may this person do" and is enforced by the security layer. A segment answers "what should this person see" and is a presentation concern. Never use a segment to hide sensitive content — the content is still served, just not shown. Use permissions for that.

Experiences

An experience is a complete alternative composition of one content page, bound to a segment. Same URL, same page, different fragments, different mapped content, different collections.

PropertyBehaviour
PriorityExperiences are ordered; the first whose segment matches wins
DefaultThe last one, matching everybody. Always exists.
ScopePer page. Not per site, not per fragment.
EditingEach experience is edited independently in the page editor
Experiences multiply your maintenance

Three experiences on a page means three compositions to update when the design changes. They do not inherit from the default. Use them where the difference is genuinely worth it — a different hero and CTA — not to vary a single word.

Cheaper alternatives to a full experience

NeedCheaper option
One block differs by audienceA collection filtered by a category the audience already implies
Language differencesLocalisation, not segmentation — Web Content is translatable per field
Signed-in vs signed-outPage permissions plus a separate page, usually clearer
Department-specific newsOne page, one collection, filtered by the user's department category

A/B testing

With Analytics Cloud connected, an A/B test runs two variants of an experience against a goal (clicks, bounce rate, conversion) and reports a winner, which you can then publish as the default.

  • Needs enough traffic to reach significance — on an intranet with 300 users, usually it does not.
  • Requires Analytics Cloud; without it you get experiences but no measurement.
  • Test one meaningful change at a time; two changes give you an unattributable result.

How it connects

  • Pages — experiences are per page
  • Fragments — what varies
  • Collections — often the cheaper variation
  • Categories — audience-aligned content filtering
  • Permissions — for anything that must be hidden, not just unshown
  • Objects — user attributes segments read

Traps

Segmentation is not security

Content excluded by a segment is still on the server and still permitted. Anyone who can guess a URL or read an API response gets it. If it must not be seen, it needs a permission.

Caching interacts with personalisation

Personalised pages cannot be cached as aggressively as static ones. A page with many experiences is a page you are serving fresh each time — worth knowing before applying it to the homepage.

Experiences are not carried by a site initializer's page upserts

Like any page composition change, adding an experience to an existing page needs a reprovision to come from source.
