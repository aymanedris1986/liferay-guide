In one sentence

An Object is a custom data model. You define fields, relationships and rules; Liferay creates the table, generates a REST API at /o/c/<plural of the object name>, gives you an admin UI, and wires it into collections, forms, workflow, search and permissions.

What you get when you publish one

Object definition "Policy" │ ├─▶ a real database table (and a second one, <table>_x, for fields added later) ├─▶ REST: GET/POST/PUT/PATCH/DELETE /o/c/policies (+ OData filter, sort, page, batch) ├─▶ an admin application in the Control Panel (layouts + views) ├─▶ a collection provider (usable in any Collection Display) ├─▶ a form target (Form Container binds to it) ├─▶ a display page template binding (one URL per entry) ├─▶ two permission resources (entry: VIEW / UPDATE / DELETE, definition: ADD_OBJECT_ENTRY) └─▶ search indexing + workflow support

That is a lot of platform for one definition, and it is the reason Objects are the default answer for anything that is data rather than prose.

Draft, then published

A definition starts as a draft: nothing exists yet except the metadata. Publishing creates the table, registers the REST application, the permission resources and the admin app. Some choices are frozen at publish time — the name (and therefore the REST path and the database table), the scope, and the storage type — so settle them in the draft. Labels can change freely afterwards.

They are not in the 2026.Q2.0 source constants (ObjectFieldConstants there has LargeFile and Assignee instead, which the docs do not list yet), so check the field-type dropdown on your own bundle before you design around any of these four.

Encrypted fields need three portal properties

Adding an Encrypted field fails with "Business type encrypted is disabled" until portal-ext.properties sets object.encryption.enabled=true, object.encryption.algorithm (e.g. AES) and object.encryption.key (a Base64 key valid for that algorithm). It only works on objects with the default storage type. Encrypted values cannot be searched or filtered — that is the point — so do not encrypt anything you will need to query.

Field names

Names must start with a lowercase letter and be at most 41 characters. The name is the REST property, the DB column (with a _ suffix) and the ObjectField_<name> binding key in forms, so pick it like an API name, not a label.

Reserved field names roll back the entire site

The reserved list (from ObjectFieldLocalServiceImpl, compared case-insensitively) is: actions, companyId, createDate, creator, currentDate, dateCreated, dateModified, displayDate, expirationDate, externalReferenceCode, groupId, id, keywords, lastPublishDate, modifiedDate, reviewDate, status, statusByUserId, statusByUserName, statusDate, taxonomyCategoryIds, userId, userName. name, email, location, company are fine. In a site initializer, a collision throws ObjectFieldNameException$MustNotBeReserved, which aborts initialization and rolls back the whole site transaction — no site, no objects, no picklists. The symptom reads as "the CET never deployed".

State fields

Marking a picklist field "state": true turns it into a lifecycle field with a state flow (which transitions from which value are allowed). It then requires a default:

{
	"businessType": "Picklist",
	"label": { "en_US": "Status" },
	"listTypeDefinitionExternalReferenceCode": "POLICY_STATUS",
	"name": "policyStatus",
	"objectFieldSettings": [
		{ "name": "defaultValue", "value": "draft" },
		{ "name": "defaultValueType", "value": "inputAsValue" }
	],
	"required": true,
	"state": true
}
Omitting the default is another silent rollback

Without defaultValue + defaultValueType you get ObjectFieldSettingValueException.MissingRequiredValues — same total rollback as a reserved name. And defaultValue must be an existing picklist entry key; a typo there rolls back too.

A state field is not the workflow status

Every entry already has a system status (approved, pending, draft…) owned by workflow. A state picklist is your business lifecycle ("submitted → in review → closed"). They are independent: a workflow can approve an entry whose state is still submitted. Decide which one your listings filter on, and do not name your field status — it is reserved for exactly this reason.

Picklists (list type definitions)

A reusable set of key/label options. Define once, reference from any object field. The key is what is stored and what filters match; the name is the translatable label.

{
	"externalReferenceCode": "POLICY_STATUS",
	"listTypeEntries": [
		{ "externalReferenceCode": "POLICY_STATUS_DRAFT", "key": "draft", "name": "Draft" },
		{ "externalReferenceCode": "POLICY_STATUS_ACTIVE", "key": "active", "name": "Active" }
	],
	"name": "Policy Status"
}

Over REST a picklist value comes back as an object ({"key": "active", "name": "Active"}); on write, sending just the key is enough.

Guest cannot read a picklist over REST

GET /o/headless-admin-list-type/…/list-type-entries returns 403 for anonymous users, and a company-scope VIEW grant does not lift it. A public form that populates a <select> by fetching the picklist renders it empty; the visitor submits blank and the entry saves looking successful. Ship the options in the fragment markup.

Relationships

oneToManyOne parent, many children (Event → Registrations)An FK column on the child

Those are the only two you can create: the source also defines oneToOne, but relationship validation accepts only oneToMany and manyToMany. For "one-to-one", use one-to-many and enforce the "one" with a validation.

{
	"deletionType": "cascade",
	"externalReferenceCode": "EVENT_REGISTRATIONS",
	"label": { "en_US": "Registrations" },
	"name": "eventRegistrations",
	"objectDefinitionId1": "[$OBJECT_DEFINITION_ID:Event$]",
	"objectDefinitionId2": "[$OBJECT_DEFINITION_ID:Registration$]",
	"objectDefinitionName2": "Registration",
	"type": "oneToMany"
}
deletionTypeDeleting the parent…Use when
prevent (the default if omitted)fails while children existChildren are valuable records (invoices, submissions)
cascadedeletes the children tooChildren are meaningless alone (registrations of a cancelled event)
disassociatekeeps the children, clears their FKChildren outlive the parent. Liferay also makes the FK field non-required, because it will be empty
The foreign key sits on the child but is named for the parent

The relationship above creates r_eventRegistrations_c_eventId on Registration — not …_c_registrationId. Set that key when creating a child over REST. Get it wrong and the unknown key is ignored: the child is created with the FK left at 0, and the POST still returns 200. There is an ERC twin, r_eventRegistrations_c_eventERC, which is what OData relationship filters need.

Relationships also get their own REST sub-resources on the parent side, which is the only way to link manyToMany entries:

GET  /o/c/events/{eventId}/eventRegistrations                  # the children
PUT  /o/c/events/{eventId}/eventRegistrations/{registrationId}  # associate

Relationships can also cross into system objects (Account, User…), which is how you hang your own data off built-in entities.

Why this matters for your workflow

Company-scoped objects and their entries survive the delete-and-redeploy cycle that page and fragment changes require. So you can iterate on pages all day without losing runtime data.

Per-definition switches worth knowing: entry history (an audit trail per entry), categorization (tags and categories on entries, which is what makes them filterable by taxonomy), comments, and localization (translatable field values).

System objects: extending what Liferay already has

Several built-in entities are exposed to the Objects framework as system objects: Account, Organization, User, Postal Address, and on Commerce, Order, Product and Product Group. You cannot change their existing fields, but you can add fields, relationships, actions and validations.

  • Added fields live in a side table named after the service table with _x appended (AccountEntry_x), so upgrades never touch them.
  • Relationships to system objects work, but system objects have no custom layouts, so the relationship appears only over headless APIs, not in their admin UI.
  • Postal Address can only relate to custom objects that are themselves related to Account.

The most useful one on a B2B project is Account: relate your object to it, turn on account restriction, and each entry becomes visible only to users of its account — row-level security you would otherwise have to build. That is where account roles come in.

The REST surface

PurposeEndpointOAuth scope
Define objects, fields, relationships, actions/o/object-admin/v1.0/object-definitionsLiferay.Object.Admin.REST.everything
Read/write entries/o/c/<plural>One per object: C_<ObjectName>.everything (e.g. C_Policy.everything)

The path is derived from the object's name, not its label: lowercased, then pluralised. Policy → /o/c/policies, PolicyRequest → /o/c/policyrequests. Renaming the label never moves the URL; the name cannot change after publish.

curl --silent --user "test@liferay.com:test" \
	--url "http://localhost:8080/o/c/policies?filter=policyStatus%20eq%20'active'&sort=title:asc&pageSize=20"

# address an entry by its stable key instead of its numeric id
curl --silent --user "test@liferay.com:test" \
	--url "http://localhost:8080/o/c/policies/by-external-reference-code/POLICY-ANNUAL-LEAVE"

Prefer external reference codes in anything that crosses environments: ids differ between your laptop and production, ERCs do not. Each object also has a /batch endpoint for bulk import.

  • Collections — how entries get listed
  • Display pages — a URL per entry
  • Workflow & actions — lifecycle logic
  • Permissions — who sees which entries
  • Microservice CETs — custom logic and storage
  • Headless APIs — the generated endpoints
  • Content Structures — the editorial alternative

Traps

A new object is invisible to everyone but its admins

The generated resource actions have empty guest-defaults and empty site-member-defaults. So after publishing, neither visitors nor ordinary signed-in users can read entries until you grant VIEW. The creator of an entry can still see it (the Owner role), which is why "I can see my test entry" proves nothing. See Guest access.

Never count object entries in the browser on a public page

A public form's object is typically write-only for Guest: ADD_OBJECT_ENTRY granted, VIEW deliberately not (company-scope VIEW would publish every submitter's name and email). So GET /o/c/<plural> returns 200 with totalCount: 0 for the visitor, and "500 of 500 seats" renders as "0 of 500".

Fix it with an Aggregation field (businessType: Aggregation, function: COUNT) on the parent object. Aggregations are computed server-side and ignore entry-level permissions, so Guest gets the right number without being able to read a single submission. It serializes as a string — parse before arithmetic. And because aggregations are not indexed, you cannot sort or filter a listing by them.

The submission POST does return the entry

Write-only is not write-blind. A Guest holding ADD_OBJECT_ENTRY and no VIEW still gets 200 with the complete created entry — id, fields, resolved picklists, the FK and its ERC twin, and workflow status. So a form can confirm back what was recorded. Do not code defensively around a body that is in fact there.

Objects are not reproducible from a site initializer alone

Definitions are company-scoped, so they persist across reprovisions — but a fresh bundle or a different environment starts without them. Either keep them in object-definitions/ or script them over object-admin; be explicit about which half of the data layer your tree actually rebuilds.

Publish before you reference

[$OBJECT_DEFINITION_ID:Name$] and [$OBJECT_DEFINITION_CLASS_NAME:Name$] tokens resolve for every published object in the company — including ones created live outside the tree. A draft definition registers no token, and the file referencing it fails to parse.

Workflow changes what "created" means

Once a workflow is attached to the object, a successful POST creates an entry with status pending, not approved. Listings, collections and non-owners will not see it until someone approves. The POST body's status tells you which case you are in.
