In one sentence

A Content Structure (in the UI: Web Content → Structures. In code and APIs it is a DDMStructure, or a content structure in Headless Delivery) is a form definition. It lists the fields a Web Content article of that kind has, their types, whether they repeat, and whether they are required.

What it actually is

Think of it as a database table definition that a non-developer can build in a drag-and-drop form builder. Create a structure called News Article with fields headline, summary, heroImage, body, publishDate, and every news article now has exactly those slots.

Structures do three jobs at once:

  1. They shape the editor form. Editors see your labels and field types, not a blank rich-text box.
  2. They make content addressable. A template can say "render heroImage"; a fragment can map an editable element to headline.
  3. They make content filterable. A dynamic collection can select "all Web Content of structure News Article", and a display page template binds to one structure.
Not the new CMS's "Content Structures"

This page covers the classic DDM structure used by Web Content. The new object-based CMS (feature-flagged on 2026.Q2, GA in 2026.Q3) also calls its schemas "content structures", but they are Object definitions with different settings (ERC, Mandatory, picklists, Select Related Content). If a learn.liferay.com page mentions Spaces, it is describing the other one. See the two-CMS note.

Where it lives

Site Menu → Content & Data → Web Content → Structures tab. Structures are scoped: a structure in the Global site is available to every site, while a site structure is only available to that site (and its child sites). Asset Libraries have their own structures too. The Actions menu on a structure is worth knowing:

  • Edit Default Values pre-fills fields for every new article of that structure.
  • Manage Templates jumps to the templates bound to it.
  • Export as JSON / Import and Override moves a definition between environments. From 2025.Q1 the export carries an external reference code, so imports match up instead of duplicating. Export and import any fieldsets first, or the import fails on missing references.
  • Permissions control who can use the structure to create articles, not just who can edit it. This is how you stop editors picking the wrong structure.

Repeatable fields, fields groups and fieldsets

Any field can be marked repeatable, which turns it into a list the editor can add rows to. Drop one field onto another in the builder to create a fields group, then make the group repeatable to get a repeating record. For example, a Link group of label + url, repeated, builds a nav block.

A fieldset is a different thing: a reusable block of fields shared by several structures (an "SEO" block or an "Author" block, say). Editing a fieldset changes every structure that uses it at once, and Liferay warns you if content already uses it. That is powerful and also a large blast radius, so treat a fieldset edit like a change to every structure it appears in.

Repeatable vs an Object

Repeatable field sets are fine for a handful of rows that belong to this one article. The moment those rows need their own permissions, their own URLs, or to be queried independently, they are records — use an Object with a relationship instead.

Short version: structures are for editorial content, objects are for data. If a human writes it and another human proofreads it, structure. If a system reads it and filters it, object.

What a structure looks like in source

In a site initializer, structures live in ddm-structures/*.xml: an XML wrapper around the same JSON the builder exports. This is abridged from Liferay's teaser-showcase initializer:

ddm-structures/leadership-profile.xml
<root>
	<structure>
		<name>Leadership Profile</name>   <!-- also becomes the structure KEY -->
		<description></description>
		<definition><![CDATA[{
			"availableLanguageIds": ["en_US"],
			"defaultLanguageId": "en_US",
			"definitionSchemaVersion": "2.0",
			"fields": [
				{
					"name": "name",
					"fieldReference": "name",
					"type": "text",
					"dataType": "string",
					"displayStyle": "singleline",
					"indexType": "keyword",
					"localizable": true,
					"repeatable": false,
					"required": true,
					"label": {"en_US": "Name"}
				},
				{
					"name": "bio",
					"fieldReference": "bio",
					"type": "rich_text",
					"dataType": "string",
					"indexType": "text",
					"localizable": true,
					"label": {"en_US": "Bio"}
				}
			]
		}]]></definition>
	</structure>
</root>

Three things follow from how the importer treats this file:

  • The <name> is used verbatim as the structure key. That is why the article JSON says "ddmStructureKey": "Leadership Profile" with a space in it. Renaming it in source creates a second structure rather than renaming the first.
  • If a structure with that key exists, it is updated in place on reprovision. Delete a field from the XML, reprovision, and it is gone from the live structure too (see the trap below).
  • An optional <layout> element holds the builder's page/row/column layout. Leave it out and Liferay stacks the fields in order.

How it connects

  • Web Content — the articles that use it
  • Web Content Template — renders its fields
  • Collections — filter by structure
  • Display Page Template — bound per structure
  • Fragments — map editables to its fields
  • Objects — the alternative

The pairing rule

A structure almost always ships with at least one template. Liferay lets a structure have several templates — a card template for listings and a full template for the display page is the standard pair.

┌──▶ Template "News Card" ──▶ used in the collection listing Structure "News Article" ─────┤ └──▶ Template "News Full" ──▶ used on the display page

Traps

Field reference, not field label

Templates and fragment mappings bind to the field's reference (its stable key), not its display label. Renaming the label is safe. Changing the reference silently breaks every template and mapping that used it, with no build error: the value just renders empty. The builder gives every new field a random reference (something like Text12345678), so rename it to something meaningful before anyone writes a template against it. Once one exists, that name is fixed.

Deleting a field deletes the data

Existing articles store values keyed by field reference. Remove the field from the structure, whether in the UI or by deleting it from ddm-structures/*.xml and reprovisioning, and those values become unreachable from editors and templates. Treat structure changes on a live site as a data migration: add the new field, copy values across (headless API or script), switch the templates over, and only then remove the old field.

Indexing matters for collections

The Searchable setting (JSON indexType, XML index-type) is Disable, Keyword or Text. Keyword indexes the whole value as one token, which is what exact-match filtering and sorting need. Text tokenizes it for full-text search. Disable keeps it out of the index entirely. The headless contentFields/<ref> eq '…' filter only works on keyword fields, and a field that isn't indexed can't drive a collection's Filter by Field or sort. None of this shows in the editor UI, so decide per field when you create it. Changing it later needs a reindex before existing articles behave.
