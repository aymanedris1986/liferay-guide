In one sentence

A Content Structure (older name: DDM Structure) is a form definition. It lists the fields a Web Content article of that kind has, their types, whether they repeat, and whether they are required.

What it actually is

Think of it as a database table definition that a non-developer can build in a drag-and-drop form builder. Create a structure called News Article with fields headline, summary, heroImage, body, publishDate, and every news article now has exactly those slots.

Structures do three jobs at once:

  1. They shape the editor form. Editors see your labels and field types, not a blank rich-text box.
  2. They make content addressable. A template can say "render heroImage"; a fragment can map an editable element to headline.
  3. They make content filterable. A dynamic collection can select "all Web Content of structure News Article", and a display page template binds to one structure.

Repeatable fields and field sets

Any field can be marked repeatable, which turns it into a list the editor can add rows to. Group several fields into a field set and make the set repeatable to get a repeating record — for example a Link field set of label + url, repeated to build a nav block.

Repeatable vs an Object

Repeatable field sets are fine for a handful of rows that belong to this one article. The moment those rows need their own permissions, their own URLs, or to be queried independently, they are records — use an Object with a relationship instead.

Short version: structures are for editorial content, objects are for data. If a human writes it and another human proofreads it, structure. If a system reads it and filters it, object.

How it connects

  • Web Content — the articles that use it
  • Web Content Template — renders its fields
  • Collections — filter by structure
  • Display Page Template — bound per structure
  • Fragments — map editables to its fields
  • Objects — the alternative

The pairing rule

A structure almost always ships with at least one template. Liferay lets a structure have several templates — a card template for listings and a full template for the display page is the standard pair.

┌──▶ Template "News Card" ──▶ used in the collection listing Structure "News Article" ─────┤ └──▶ Template "News Full" ──▶ used on the display page

Traps

Field reference, not field label

Templates and fragment mappings bind to the field's reference (its stable key), not its display label. Renaming the label is safe; changing the reference silently breaks every template and mapping that used it, with no build error — the value simply renders empty.

Deleting a field deletes the data

Existing articles store values keyed by field reference in their XML. Remove the field from the structure and those values become unreachable. Treat structure changes on a live site as a data migration.

Indexing matters for collections

index-type="keyword" makes a field filterable and sortable; index-type="text" makes it full-text searchable. A field indexed the wrong way will not be offered as a sort or filter option in a dynamic collection, and the cause is invisible in the UI.
