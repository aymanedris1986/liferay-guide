In one sentence

A page is a URL in a site's navigation tree, with a type that decides how its body is produced — composed from fragments, filled with widgets, or pointed somewhere else entirely.

The page types

TypeWhat it isUse for
Content PageFragment-composed layout, edited in the page editor. The default.Everything, unless you have a specific reason not to
Widget PageLegacy portlet layout with column templatesOld portlet apps; compatibility only
Link to URLA navigation node that redirectsExternal links inside the menu
EmbeddedAn iframe to an external URL, inside your chromeWrapping a third-party tool
Full Page ApplicationOne widget occupying the whole page, own URL spaceAn app-like experience
Three "type" vocabularies — do not mix them

The internal layout key is content/portlet/url/embedded. The headless-admin-site API enum is ContentPage/WidgetPage/LinkToURLPage/EmbeddedPage/PageSetPage/LinkToPagePage. A site initializer page.json uses Content/Portlet/URL/Embedded. And headless-delivery has its own pageType field. Copying a value from the wrong table is a 400 at best and a wrong page type at worst.

Public vs private, hidden vs visible

FlagMeaning
private: falseIn the public page set. Still needs a Guest VIEW grant to actually be public — see Permissions.
private: trueIn the private page set; requires site membership.
hidden: trueReachable by URL, omitted from navigation. Used for display-page hosts and thank-you pages.

What a Content Page really is

A tree of page elements. Every content page has exactly one Root; everything else nests inside it.

Element typeRole
RootThe top of the tree
SectionA layout band: columns, spacing, background
Row / ColumnDefinitionGrid structure inside a section
FragmentA fragment placement, by key + siteKey
WidgetA portlet embedded in a content page
CollectionA Collection Display, bound via collectionConfig
CollectionItemThe per-row template inside a Collection
DropZoneOn a master page: where the page's own body is injected
FormA Form Container bound to an object definition

Minimum viable page definition:

{
	"pageElement": { "pageElements": [], "type": "Root" },
	"version": "1.0"
}

Selecting a master and adding a fragment:

{
	"pageElement": {
		"pageElements": [
			{
				"definition": { "fragment": { "key": "home-hero", "siteKey": "[$GROUP_KEY$]" } },
				"type": "Fragment"
			}
		],
		"type": "Root"
	},
	"settings": { "masterPage": { "key": "badael-master" } },
	"version": 1.1
}

Page metadata (page.json)

{
	"friendlyURL": "/home",
	"hidden": false,
	"name": "Home",
	"name_i18n": { "en_US": "Home" },
	"permissions": [ { "actionIds": ["VIEW"], "roleName": "Guest", "scope": 4 } ],
	"private": false,
	"type": "Content"
}

scope: 4 is SCOPE_INDIVIDUAL — this page only. The scope table explains the other values, and why the wrong one silently grants nothing.

Navigation

Two independent things put links in a menu:

  1. The page hierarchy. The Classic theme's navbar renders non-hidden public pages on its own, whether or not you define a menu.
  2. Navigation menus. Explicit, ordered menus defined in site-navigation-menus.json, whose items are layout, url, node, or display-page.
[
	{
		"auto": false,
		"externalReferenceCode": "BADAEL_MAIN_MENU",
		"menuItems": [
			{ "externalReferenceCode": "NAV_HOME", "friendlyURL": "/home", "privateLayout": false, "type": "layout" }
		],
		"name": "Main Menu",
		"typeSite": 1
	}
]
A bad friendly URL is skipped, not reported

A layout menu item is resolved by friendly URL. No match logs "No layout found with friendly URL /whatever" and the item is dropped — the menu still provisions, just shorter. Count items over REST after provisioning rather than trusting the build.

How it connects

  • Fragments — the building blocks
  • Collections — lists on a page
  • Master pages — the chrome
  • Page templates — the starting layout
  • Display pages — auto-generated per item
  • Style books — how it looks
  • Permissions — who can see it
  • Experiences — variants of the same page
  • Headless APIs — creating pages programmatically

Creating pages via API

POST /o/headless-admin-site/v1.0/sites/{siteExternalReferenceCode}/site-pages
ERC, not numeric ID

headless-admin-site keys sites by external reference code in the path. A numeric site ID returns 404 — which reads as "the endpoint does not exist" and sends people hunting for a feature flag. (headless-admin-content and headless-delivery, confusingly, do use numeric siteId.)

Feature flags gate the page APIs

LPD-35443 for public layouts (off by default), LPD-38869 for private (on), LPD-39244 for fragment/page composition, LPD-74328 for page-element creation (depends on LPD-35443). A 404 from a page endpoint usually means a flag, not a typo.

Traps

Page composition changes need a full reprovision

Re-triggering a site initializer upserts pages but does not retrofit composition changes onto pages that already exist. Editing page-definition.json for an existing page does nothing until the site is deleted and recreated.

Deleting the site does not delete your objects

Object definitions and entries are company-scoped and survive site deletion — so reprovisioning is safe for runtime data. The exception is an object explicitly scoped to the site; those entries go with it.
