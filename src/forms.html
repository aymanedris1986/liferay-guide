In one sentence

A modern Liferay form is a Form Container page element bound to an Object definition, containing input fragments each bound to one object field, plus a submit button. Submitting creates an object entry.

The composition

{
	"definition": {
		"formConfig": {
			"formReference": { "className": "[$OBJECT_DEFINITION_CLASS_NAME:PolicyRequest$]", "classType": 0 }
		},
		"layout": { "widthType": "Fluid" }
	},
	"type": "Form",
	"pageElements": [
		{ "definition": { "fragment": { "key": "INPUTS-text-input" },
			"fragmentConfig": { "inputFieldId": "ObjectField_subject" } }, "type": "Fragment" },
		{ "definition": { "fragment": { "key": "INPUTS-select-from-list" },
			"fragmentConfig": { "inputFieldId": "ObjectField_requestStatus" } }, "type": "Fragment" },
		{ "definition": { "fragment": { "key": "INPUTS-submit-button" },
			"fragmentConfig": { "buttonSize": "nm", "buttonType": "primary" } }, "type": "Fragment" }
	]
}

Two conventions carry the whole thing: the container names the object by class name token, and every input names its field as ObjectField_<fieldName>.

Built-in input fragments

KeyBinds to
INPUTS-text-inputText, LongText, Integer, Decimal, Email
INPUTS-select-from-listPicklist fields and relationship fields
INPUTS-date-inputDate / DateTime
INPUTS-checkbox, INPUTS-radioBoolean, small enumerations
INPUTS-attachmentAttachment fields
INPUTS-captchaCAPTCHA verification
INPUTS-submit-buttonSubmits the container

A relationship field is selected exactly like a picklist — inputFieldId: "ObjectField_r_ticketToProject_c_projectId" gives the visitor a picker over the related object's entries.

Custom input fragments

When the built-in inputs are not enough — a stepper, a card picker, a dependent dropdown — write a fragment of type input. It declares which field type it accepts and Liferay handles the binding and submission; you own the markup and behaviour.

Custom inputs must live inside a Form Container

An input fragment placed outside a container has nothing to bind to. It will render, and it will submit nothing.

Public forms — the rules that matter

A form open to anonymous visitors has a specific permission shape, and getting it wrong either breaks the form or leaks data.

Grant to GuestOn resourceVerdict
ADD_OBJECT_ENTRYcom.liferay.object#[$OBJECT_DEFINITION_ID:X$]Required — without it, submission fails
VIEW[$OBJECT_DEFINITION_CLASS_NAME:X$]Do not grant at company scope — it publishes every submission to the world
UPDATE, DELETE, PERMISSIONSeitherUngrantable to Guest at any scope

So a public form is write-only: visitors can submit, and cannot read back the collection. Full detail on Guest access.

Handling the response correctly

The visitor's own POST does return the created entry — complete body, HTTP 200, even with no VIEW. So confirm back what was recorded rather than coding around an absent body. Guard the parse, though, because a 500 or a proxy error may return HTML:

const response = await fetch(`/o/c/policyrequests`, {
	body: JSON.stringify(payload),
	headers: {'Content-Type': 'application/json'},
	method: 'POST'
});

const raw = await response.text();
let body;

try {
	body = JSON.parse(raw);
}
catch (error) {
	throw new Error(`Unexpected response (HTTP ${response.status})`);
}

if (!response.ok) {
	throw new Error(body.title || body.detail || `HTTP ${response.status}`);
}

How it connects

  • Objects — where submissions land
  • Fragments — the inputs
  • Pages — where the container sits
  • Workflow — approval after submit
  • Guest access — the rules above
  • Aggregation fields — counting submissions safely

Traps

A picklist fetched from public JS renders empty

Guest gets 403 on the list-type endpoint regardless of grants. The <select> renders with no options, the visitor submits blank, and the entry saves looking fine. Ship options in the fragment markup; let any fetch merely refresh them.

A silently ignored relationship key

If the form writes the FK by hand, the key is r_<relationshipName>_c_<parent>Id — named for the parent, on the child. A wrong key is ignored, the FK stays 0, and the POST returns 200. The submission looks successful and is orphaned.

Do not show counts or totals from the form's own object

"142 people have registered" computed in the browser reads 0 for Guest. Put the number on a readable parent object via an Aggregation field.
