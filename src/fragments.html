In one sentence

A fragment is a small, self-contained piece of a page — a hero, a card row, a CTA — written in plain HTML/CSS/JS, with declared configuration options and editable elements, that a non-developer can drop onto a content page and adjust without touching code.

Anatomy

fragments/group/<collection-key>/ ← the directory name IS the set key ├── collection.json {"name": "Badael Home", "description": "…"} ├── resources/ images/fonts shared by the set (optional) │ └── hero-bg.jpg referenced as [resources:hero-bg.jpg] └── fragments/ └── home-hero/ ← the directory name IS the fragment key ├── fragment.json name, type, file pointers ├── index.html the markup (FreeMarker runs here) ├── index.css styles (NOT scoped, NOT FreeMarker) ├── index.js behaviour (optional) ├── configuration.json the options editors see (optional) └── thumbnail.png sidebar preview (optional)

The file names are not magic — fragment.json points at them. These are the keys the importer actually reads (FragmentsImporterImpl, 2026.Q2):

{
	"cacheable": false,
	"configurationPath": "configuration.json",
	"cssPath": "index.css",
	"htmlPath": "index.html",
	"icon": "square",
	"jsPath": "index.js",
	"name": "Home Hero",
	"thumbnailPath": "thumbnail.png",
	"type": "component"
}

There is no key field: the fragment key is the directory name, and that key is what page definitions reference. cacheable: true lets Liferay cache the rendered HTML — only safe for fragments whose output does not depend on the user, the request, or [#if] logic over live data.

A missing or misspelled "type" silently makes it a section fragment

FragmentConstants.getTypeFromLabel recognises component, input, react and widget; anything else — no type at all, or a typo such as "compnent" — falls back to section, the legacy type. Always write "type": "component" explicitly. See the section-fragment warning below for why that matters.

Editable elements — where content actually enters

Mark any element editable and the page editor lets someone change it in place:

<h2 data-lfr-editable-id="hero-title" data-lfr-editable-type="text">
	Welcome to Badael
</h2>

<img data-lfr-editable-id="hero-image" data-lfr-editable-type="image" src="placeholder.png" alt="">

<a data-lfr-editable-id="hero-cta" data-lfr-editable-type="link" href="#">Read more</a>
data-lfr-editable-typeEditor gets
textPlain text, inline. HTML is stripped.
rich-textA formatting toolbar. Put it on a block element such as <div>, not <p> — the content itself contains block elements.
imageMedia picker (Documents & Media) or URL; alt text
linkURL, page picker, or a mapped field; target
htmlRaw markup
date-timeA date, typically mapped to a date field, with a display format
actionA button that triggers an Object action on the mapped entry

Background images are an attribute, not an editable type

There is no backgroundImage value for data-lfr-editable-type. An editable background is a separate attribute on the container:

<div class="badael-hero" data-lfr-background-image-id="hero-bg">
	<h1 data-lfr-editable-id="hero-title" data-lfr-editable-type="text">Welcome</h1>
</div>

The editor gets an image picker in the fragment's sidebar and Liferay writes the chosen image as an inline background-image. It can be mapped like any image editable, which is how a display page hero takes the article's own image.

Editable IDs are storage keys — treat them as a public API

Whatever an editor typed or mapped is stored against data-lfr-editable-id in each placement's editable values. Rename the ID and existing placements lose that content the next time the fragment code reaches them. IDs must be unique within the fragment, and editables cannot be nested inside other editables.

Mapping — the part people miss

An editable element does not have to hold typed text. It can be mapped to a field of a content item, which is how one fragment renders a thousand different records:

  • Map to a specific Web Content field → "always show the CEO letter's title here".
  • Map to the current item on a display page template → the fragment renders whichever record the URL points at.
  • Map to the collection item inside a Collection Display → one card fragment, N rows.

Mapped fragments are what turn a static design into a CMS. A fragment with only typed-in text is a nicely styled dead end.

The mapping panel only offers fields compatible with the editable's type — an image editable lists image fields, not text. So choose the editable type for what the field is, not for how it looks.

Drop zones — fragments that hold other fragments

A fragment can reserve areas where editors drop other fragments and widgets:

<div class="badael-two-col">
	<aside><lfr-drop-zone data-lfr-drop-zone-id="side"></lfr-drop-zone></aside>
	<main><lfr-drop-zone data-lfr-drop-zone-id="main"></lfr-drop-zone></main>
</div>

Give every drop zone a data-lfr-drop-zone-id. Without it, content is matched to zones by position, so inserting a new zone between two existing ones shifts everything placed in them into the wrong zone. Custom elements cannot self-close — write <lfr-drop-zone></lfr-drop-zone>, not <lfr-drop-zone/>. In a page definition, the contents of a zone appear as a FragmentDropZone page element.

Use drop zones for genuine layout shells (tabs, accordions, two-column bands). For a plain grid the built-in Container and Grid elements are better — they have responsive and spacing settings you would otherwise rebuild.

Embedding widgets

<lfr-widget-nav></lfr-widget-nav>, <lfr-widget-web-content>, <lfr-widget-asset-list> and friends embed a widget directly in the fragment markup. Handy for a header fragment that must always contain the menu; each embedded widget keeps its own portlet preferences per placement.

	Heading Example

[/#if]

The collection variable name comes from the field name. A field called collection yields collectionObjectList; one called featured yields featuredObjectList. Guard it, because it is absent until an editor picks something:

[#if collectionObjectList??]
	<ul>
	[#list collectionObjectList as item]
		<li>${item.title}</li>
	[/#list]
	</ul>
[/#if]

A collectionSelector is the "code it yourself" alternative to a Collection Display: full control of the markup, but no editor-side mapping, pagination, or filter fragments. Prefer the Collection Display unless the markup genuinely cannot be expressed as per-item fragments.

FreeMarker in fragments — what is different from templates

  • Square-bracket syntax only. Liferay prepends [#ftl] to the HTML, which switches FreeMarker to square-bracket tags. [#if], [#list], [#assign] work; <#if> is emitted as literal text. ${…} interpolation is unaffected.
  • HTML only. FreeMarker runs on index.html. It does not run on index.css or index.js — the CSS only has [resources:…] substitution.
  • Variables available: configuration, fragmentElementId, fragmentEntryLinkNamespace, fragmentName, layoutMode (view/edit), the …Object/…ObjectList helpers above, input for input fragments, and the usual themeDisplay context.
  • It can be switched off. FreeMarker processing for fragments is an instance-level setting (FreeMarkerFragmentEntryProcessorConfiguration); with it off, custom fragments render their template text unprocessed. If ${…} shows up literally on a page, check this first.

Fragment JavaScript

Your index.js is wrapped per placement — in an IIFE, or a <script type="module"> when JS modules are enabled — with these constants already declared:

ConstantWhat it is
fragmentElementThe wrapper <div> of this placement. Query inside it, never the document.
configurationThe same values as FreeMarker's configuration, as a JS object
fragmentElementIdThe wrapper's DOM id
fragmentEntryLinkNamespaceA per-placement unique string (fragmentNamespace is the deprecated alias)
layoutMode'view' or 'edit' — skip carousels, timers and redirects in edit mode
inputInput fragments only: field name, value, errors, required flag
// index.js — runs once for every placement of the fragment
const button = fragmentElement.querySelector('.badael-hero__toggle');

if (layoutMode === 'view' && button) {
	button.addEventListener('click', () => {
		fragmentElement.classList.toggle('is-open');
	});
}

Because every placement gets its own copy, document.querySelector('.badael-hero') in fragment JS is a bug the moment the fragment is placed twice: both copies grab the first one.

Section fragments break the fragment listing API

One fragment with type section makes the whole set's headless-admin-fragment listing return 400. Verified on 2026.Q2. Harmless for rendering, annoying for tooling — and because a missing type is section, one forgotten line in one fragment.json is enough.

How it connects

  • Pages — where fragments are placed
  • Collections — fragments render each item
  • Master pages — header/footer fragments
  • Display pages — fragments map to the current item
  • Web Content — what editables map to
  • Objects — mapped fields, actions and form inputs
  • Style books — the tokens fragment CSS should use
  • Experiences — different fragments per audience
  • Site initializers — where fragment source lives

Fragment sets (aka fragment collections)

Fragments live in named sets, which is just how the sidebar groups them. In an initializer tree the set is the directory under fragments/group/ with a collection.json (name, description). Group by purpose — Chrome, Home, Cards — not by page, because fragments get reused across pages.

A set can also carry a resources/ folder. Files there are imported alongside the set and referenced from HTML or CSS as [resources:hero-bg.jpg], which Liferay rewrites to the stored file's URL — the clean way to ship a background image or icon with the fragment instead of hard-coding a Documents & Media URL.

Traps

Editing a fragment does not update pages that already use it

Liferay copies fragment code into each placement (a fragment entry link) at placement time. Changing the source — in the tree, in the UI, or via the headless-admin-fragment API — updates the library entry and leaves every existing placement untouched. That is deliberate: a typo in the library should not rewrite every live page at once.

Ways to get the change onto pages: in Design → Fragments, open the fragment's Usages and Propagate; or, for development only, enable System Settings → Page Fragments → Propagate Fragment Changes Automatically; or rebuild the pages from source by reprovisioning the site. Built-in (contributed) fragments are the exception — they always render the current code. This surprises everyone exactly once, usually for an afternoon.

Wrong keys in a page definition render a blank page

In page-definition.json a fragment is referenced by key (its directory name) plus siteKey ([$GROUP_KEY$]). Writing collectionExternalReferenceCode/fragmentEntryKey instead is silently dropped — the page provisions successfully and renders empty. Built-in fragments use a combined key with no siteKey, e.g. BASIC_COMPONENT-paragraph.

Fragment CSS is global, and it is not a template

index.css is emitted as a plain <style> block, once per fragment per page, with no automatic scoping — your .card rule restyles every .card on the page. FreeMarker does not run in it, so ${fragmentEntryLinkNamespace} in CSS stays literal. Prefix every selector with a fragment-specific class (.badael-hero …). For per-placement values, put them on the markup in index.html, e.g. style="--hero-bg: ${configuration.bgColor}", and read var(--hero-bg) in the CSS.

Fragment JS runs as the visitor

Any fetch you write executes with the visitor's session. What returns data for you may return 403 or an empty list for Guest. See Guest access before building anything data-driven on a public page.

Editor-mode JS runs too

Your script also runs inside the page editor. A carousel that auto-advances, a redirect, or code that removes editable elements will fight the editor. Guard behaviour with layoutMode === 'view'.
