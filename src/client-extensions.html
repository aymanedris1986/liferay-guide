In one sentence

A Client Extension (CET) is a unit of customisation declared in a client-extension.yaml and deployed as a zip or a container. It either injects assets into the browser, registers configuration, imports data, or exposes an HTTP endpoint Liferay calls — but it never runs inside Liferay's JVM.

Why this matters

Because CETs live outside the platform, they survive upgrades, work on SaaS, deploy independently, and can be written in any language. That is the whole reason to prefer them over OSGi modules.

The four classifications

FRONTEND assets injected into the browser (CSS, JS, custom elements, themes) CONFIGURATION OAuth apps and typed settings (no code, no endpoint) MICROSERVICE an HTTP endpoint Liferay calls INBOUND (object actions, validators, workflow) BATCH bulk data import / whole-site setup (batch, siteInitializer)

Which types may share one project

This is enforced by the workspace Gradle plugin, and the failure appears late — after the assemble tasks have already printed success.

Allowed groupingCovers
configurationOAuth apps and instanceSettings alone
configuration + batchA batch or siteInitializer with its OAuth companion
configuration + frontendTheme, CSS, JS, custom elements, with OAuth if needed
configuration + microserviceHandlers with OAuth
batch, frontend and microservice can never be combined

Add a themeCSS to your siteInitializer project and the build fails at createClientExtensionConfig:

The combination of client extensions in [configuration, batch, frontend] cannot be
grouped in a single project.

A complete site is several sibling projects, not one. Expect at least: the initializer + its OAuth, a frontend project for theme/CSS, and a microservice project per handler group. A batch/siteInitializer project must also contain exactly one oAuthApplicationHeadlessServer and at most one batch/initializer entry.

Microservice types

These expose an HTTP endpoint that Liferay calls inbound. Each needs an oAuthApplicationUserAgent companion that carries .serviceAddress and .serviceScheme; each CET entry carries its own resourcePath.

objectActionAn object entry is added/updated/deleted, or an action is invokedLiferay.Headless.Object.everything
objectValidationRuleBefore an entry saves; you return pass/fail and block the saveLiferay.Headless.Object.everything
objectEntryManagerEvery CRUD call on an ext-Service object — you are the storageLiferay.Headless.Object.everything
workflowActionA Kaleo workflow reaches an action nodeLiferay.Headless.Admin.Workflow.everything
notificationTypeA notification of your custom channel firesLiferay.Headless.Object.everything
captchaA form needs CAPTCHA verificationnone
commercePaymentIntegration / commerceShippingEngine / commerceTaxEngineCheckout needs a gateway, rate, or tax figureCommerce scopes

    allowedObjectDefinitionNames:
        -   C_Employee
The token flows both ways

Liferay calls your endpoint with a Bearer token, and that token is what your service uses to call back into Liferay's Headless APIs — as the acting user, with their permissions. That is why the companion is a UserAgent app and not a server app.

Configuration types

TypePurpose
oAuthApplicationHeadlessServerService-account OAuth app — the CET calls into Liferay. Used by batch and siteInitializer.
oAuthApplicationUserAgentUser-delegated OAuth app — Liferay calls out to the CET and passes a token. Used by microservice CETs.
instanceSettingsTyped OSGi configuration deployed as a .config file, editable in Instance Settings

The direction of the call is the whole distinction, and it is the single most common cause of a CET that deploys cleanly and authenticates against nothing.

Batch types

TypePurpose
batchBulk data import through the Batch Engine (JSON files with a configuration.className envelope)
siteInitializerA whole site from source: pages, fragments, objects, roles, content — see Site initializers
There is no batch/ directory inside a site initializer

*.batch-engine-data.json files placed in an initializer tree are packaged into the zip and silently ignored. The build succeeds, the site provisions, no data appears. That envelope belongs to the separate batch CET type.

Minimum viable examples

# globalCSS
badael-global-css:
    name: Badael Global CSS
    scope: company
    type: globalCSS
    url: global.*.css
# themeCSS
badael-home-theme-css:
    clayRTLURL: css/clay_rtl.css
    clayURL: css/clay.css
    mainRTLURL: css/main_rtl.css
    mainURL: css/main.css
    name: Badael Home Theme CSS
    type: themeCSS
# siteInitializer + its OAuth companion
badael-site-init:
    name: Badael Site Initializer
    oAuthApplicationHeadlessServer: badael-site-oauth
    siteExternalReferenceCode: badael
    siteName: Badael Site
    type: siteInitializer

badael-site-oauth:
    .serviceAddress: localhost:8080
    .serviceScheme: http
    name: Badael Site OAuth
    scopes:
        - Liferay.Headless.Admin.Site.everything
        - Liferay.Headless.Admin.Content.everything
        - Liferay.Object.Admin.REST.everything
        - Liferay.Headless.Object.everything
        - Liferay.Headless.Admin.User.everything
    type: oAuthApplicationHeadlessServer

Building and deploying

cd client-extensions/<name>
blade gw deploy

The assemble block says what gets packaged:

assemble:
    - from: site-initializer
      into: site-initializer
assemble:
    -   fromTask: bootJar      # a Spring Boot microservice CET
BUILD SUCCESSFUL is not verification

Success means the zip was produced. Confirm the bundle reached STARTED in the log, and for an initializer confirm the Initializing <Site> count actually increased. Gradle's up-to-date check is content-based, so with no source edit a redeploy rewrites nothing at all.

How it connects

  • Objects — what most microservice CETs hook into
  • Workflow & notifications — the other hook points
  • Site initializers — a CET that builds a site
  • Themes — themeCSS and style books
  • Fragments — the lighter-weight alternative
  • OSGi modules — when a CET is not enough
  • Headless APIs — what CETs call

Traps

Wrong OAuth type = silent auth failure

oAuthApplicationHeadlessServer for CETs that call into Liferay; oAuthApplicationUserAgent for CETs Liferay calls. Getting it backwards deploys fine and fails at the first request.

401 vs 403

403 means the token is valid but its scopes do not cover the endpoint — add the scope and redeploy. 401 means the token itself is wrong — check the OAuth registration, not the scopes.

Unknown scope strings fail the deploy

Liferay validates the scopes list on deploy. Also note the object split: Liferay.Object.Admin.REST.everything is for definitions (/o/object-admin/…); Liferay.Headless.Object.everything is for entries (/o/c/<plural>). Most handlers only need the second.
