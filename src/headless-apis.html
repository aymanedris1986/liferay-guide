What "headless" means here

Liferay's REST APIs are generated from OpenAPI specs by its REST Builder, on a shared framework (Vulcan). That matters because it is why every module behaves the same way: the same page/pageSize, the same filter/sort/search, the same fields/nestedFields, a /batch variant of most write operations, and a GraphQL mirror of most of it. Learn the conventions once and they apply to every module below.

/o/<module>/v1.0/<resource> REST, one JAX-RS application per module /o/c/<objectPlural> REST for each published Object (one app per object) /o/graphql GraphQL over the same resources /o/api API Explorer: browse and try every module, logged in as you /o/<module>/v1.0/openapi.json the spec (also .yaml)

ERC vs numeric ID — this costs everyone an hour

headless-admin-site and headless-admin-fragment key everything by external reference code: /sites/{siteExternalReferenceCode}/site-pages. A numeric site ID returns 404, which reads like "the endpoint does not exist" and sends you hunting a feature flag.

headless-admin-content, headless-delivery and headless-admin-taxonomy, in the same product, use the numeric {siteId}. Most of those also offer by-external-reference-code/{erc} sub-paths for individual items, so you can still write scripts that never hard-code a numeric ID.

PUT by ERC is the idempotent write

Wherever a resource offers PUT …/by-external-reference-code/{erc}, it creates the record if the ERC is new and replaces it if it exists. Scripts and integrations built on that pattern can be re-run safely; scripts built on POST create duplicates or fail with 409 the second time.

Common parameters

ParameterValues
page / pageSize1-based; default page size 20. The maximum is the instance's page size limit (default 500, Instance Settings → Headless API). A larger value is silently clamped, not rejected.
filterOData subset: title eq 'Hello', dateCreated gt 2026-01-01T00:00:00Z, contains(title,'leave'), startswith(name,'A'), status in (0, 2), combined with and/or/not; collection fields support any/all lambdas. Only fields the resource declares as filterable work.
sortfieldName:asc / fieldName:desc, comma-separated for several
searchKeyword search through the search index, not a database LIKE
fieldsWhitelist: return only these (dot notation for nested, e.g. fields=id,title,creator.name)
restrictFieldsBlacklist: return everything except these (e.g. restrictFields=actions,contentFields)
nestedFieldsExpand related records inline — for objects, the relationship name; nestedFieldsDepth controls how deep
Accept-Language headerWhich locale localized fields come back in (e.g. ar-SA)
X-Accept-All-Languages: true headerAlso return *_i18n maps with every translation
# Leave requests longer than 3 days, newest first, lean payload,
# with the related employee (relationship named "employee") inlined
curl -s -u test@liferay.com:test -H 'Accept-Language: en-US' \
  'http://localhost:8080/o/c/leaverequests?filter=days%20gt%203&sort=dateCreated:desc&fields=id,startDate,days,employee&nestedFields=employee&pageSize=50'

URL-encode the filter (spaces as %20); an unencoded quote or space is the usual cause of a 400 that "works in the API Explorer".

The actions block is your permission oracle

Every item (and the page itself) carries an actions map of the operations the current caller may perform, with their URLs. A UI should render buttons from it instead of re-implementing permission logic. It is also the bulk of many payloads, which is why restrictFields=actions is a cheap win for read-only integrations.

Batch: bulk writes and exports

For anything beyond a few hundred records, do not loop over POST. Two options:

OptionPathUse when
Resource batch endpointPOST /o/c/policies/batch, POST /o/headless-delivery/v1.0/sites/{siteId}/structured-contents/batchYou have a JSON array of one resource type
Batch engine taskPOST /o/headless-batch-engine/v1.0/import-task/{className}; export via export-task/{className}/{contentType}Files (JSON, JSONL, CSV), exports, or explicit strategies

Both are asynchronous: the response is an import task with an ID and a status (STARTED, COMPLETED, FAILED). Poll GET /o/headless-batch-engine/v1.0/import-task/{id} and fetch …/failed-items/report for per-row errors. Strategy query parameters decide what re-runs do: createStrategy=UPSERT|INSERT, updateStrategy=UPDATE|PARTIAL_UPDATE, importStrategy=ON_ERROR_FAIL|ON_ERROR_CONTINUE. The same engine is behind the batch CET.

A 200 from a batch call means "accepted", not "imported"

A batch where every row failed still answers the initial request with success. Always read the task's final status and failed-items report.

Authentication, in practice

CallerUseWhy
You, in curl, locallyBasic authFast; but no scopes are evaluated
A server integration or jobOAuth2 client credentials (oAuthApplicationHeadlessServer, or an app created in OAuth 2 Administration)Service account, least-privilege scopes
A microservice CET Liferay callsThe JWT Liferay sends (oAuthApplicationUserAgent)Acts as the triggering user
Browser JS on a Liferay page (fragment, custom element)The session cookie + x-csrf-token: Liferay.authTokenRuns as the visitor, with the visitor's permissions

# client-credentials token, then call
TOKEN=$(curl -s -X POST http://localhost:8080/o/oauth2/token \
  -d grant_type=client_credentials -d client_id="$ID" -d client_secret="$SECRET" | jq -r .access_token)
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:8080/o/headless-admin-user/v1.0/my-user-account

Discovering endpoints

GET /o/api                                  # API Explorer (sign in first)
GET /o/<module>/v1.0/openapi.json           # or openapi.yaml

The spec gives you exact paths, parameters and payload shapes. It does not tell you the ERC-vs-ID convention, the feature-flag gates, or the OAuth scope names — those come from the tables above. Object entries have their own spec per object: /o/c/<plural>/openapi.json.

How it connects

  • Objects — the generated entry API
  • Pages — creating layouts programmatically
  • CETs — what calls these, and with which token
  • Service Access Policies — the gate before permissions
  • Site initializers — the declarative alternative, itself an API call
  • Fragments — browser-side calls run as the visitor

Traps

Object entry scopes are per object

Each published object registers its own JAX-RS application, so /o/c/policies has its own scope, named after the object. Pick it from the scope list in OAuth 2 Administration and copy the exact string. Liferay.Headless.Object.everything exists but belongs to /o/headless-object (object entry folders), and does not authorise /o/c/….

Editing a fragment over the API does not change any page using it

Liferay copies fragment code into each page's fragment instance. A PUT updates the library entry and leaves every existing placement untouched until someone propagates it (the fragment's Usages view in the UI). Reprovision to apply fragment changes from source.

Basic auth hides scope problems

Your curl as test@liferay.com has full admin rights and evaluates no scopes. The same call from a CET with a narrow token returns 403. Test the CET path before declaring it works.

One denied row can break an object listing

Observed on this project: when entry-level permissions make one row of GET /o/c/<plural> unviewable, the per-row VIEW check can fail the whole page instead of dropping the row. If lists 404 or error for some users only, suspect per-entry permissions before the query.

One section fragment breaks the fragment listing

A single fragment declaring "type": "section" makes the whole set's listing return 400. Verified on 2026.Q2.
