In one sentence

A site initializer is a client extension of type siteInitializer whose directory tree describes an entire site — pages, fragments, objects, roles, permissions, content, style books — and creates or updates it on deploy.

The principle

The initializer tree is the single source of truth. Build the site by triggering the initializer; iterate by editing the source and reapplying. Never hand-edit the live site as the authoritative copy.

Both are executed by the same class, BundleSiteInitializer, so the folder layout, handlers, tokens and log lines below apply to both. Liferay's own bundled initializers are the best reference for file formats you cannot find documented — they ship in osgi/portal/com.liferay.site.initializer.*.jar.

How deploying one actually works

zip lands in osgi/client-extensions/ │ file-install watcher sees a new or CHANGED zip ▼ SiteInitializerClientExtension │ builds a Site DTO (name, ERC, membershipType, parentSiteKey) + the site-initializer.zip ▼ headless-admin-site: PUT /sites/{siteExternalReferenceCode}/site-initializer │ "adds or updates" the site ▼ BundleSiteInitializer.initialize(groupId) │ Initializing … → Invoking <handler> took N ms … → Initialized … in N ms

Two consequences worth internalising:

  • The deploy is an API call you can make yourself. PUT /o/headless-admin-site/v1.0/sites/{siteERC}/site-initializer with a multipart file applies a zip without touching the file-install folder, and GET on the same path exports an existing site as a site-initializer zip — a fast way to bootstrap a tree from a site someone built by hand.
  • A re-run is an update, not a rebuild. Handlers are named addOrUpdate… for a reason: they upsert by key or ERC into the existing site. That is why some changes apply on reapply and others (below) need the site deleted first.
badael-site-init:
    membershipType: private         # open (default) | restricted | private
    name: Badael Site Initializer
    oAuthApplicationHeadlessServer: badael-site-oauth
    siteExternalReferenceCode: badael      # required — the site's identity forever
    siteName: Badael Site                  # required — also the log key
    type: siteInitializer
Pick the ERC once

siteExternalReferenceCode is how every future deploy finds the site. Change it and the next deploy creates a second site instead of updating the first.

The tree

client-extensions/<name>/ ├── client-extension.yaml └── site-initializer/ ← required; the plugin fails without it ├── documents/group/<folder>/… media (documents/company for instance-wide) ├── ddm-structures/ web content structures ├── ddm-templates/ web content templates (ddm-template.json + .ftl) ├── fragments/group/<collection-key>/ (fragments/company for global sets) │ ├── collection.json │ └── fragments/<fragment-name>/… ← "fragments" nesting level is required ├── journal-articles/<name>.{json,xml} web content: metadata JSON + content XML ├── layout-page-templates/ │ ├── display-page-templates/<name>/ │ └── master-pages/<name>/ master-page.json + page-definition.json ├── layout-set/public/metadata.json theme + chrome settings ├── layout-utility-page-entries/ 404, error, terms pages ├── layouts/<NN-page>/ NN prefix controls creation order │ ├── page.json │ ├── page-definition.json │ └── <NN-child-page>/… nested pages ├── list-type-definitions/<name>.json picklists ├── object-definitions/<NN-name>.json ├── object-folders/, object-relationships/, object-fields/, object-actions/, object-entries/ ├── notification-templates/ ├── resource-permissions.json role grants ├── roles.json ├── sap-entries.json service access policies ├── segments-entries.json, segments-experiences/ ├── site-navigation-menus.json ├── site-settings.json, site-configuration.json ├── style-books/<name>/style-book.json ├── taxonomy-vocabularies/group/ vocabularies + categories ├── user-accounts.json, user-groups.json, user-roles.json, organizations.json ├── workflow-definitions/ └── thumbnail.png

The full set of paths the handler looks for is larger still (accounts, blogs, knowledge base, depot entries, expando columns, language overrides, asset lists). If a directory is not listed in the handler, it is not an error to have it — it is silently ignored, which is exactly the problem.

Each file holds a single raw DTO — usually the same JSON shape the matching headless API accepts — with no configuration wrapper and no items array.

Handler order is a dependency graph, not a list

Handlers do not run in folder order. The initializer resolves which handlers depend on which (it even detects circular dependencies) and runs them accordingly. A real run on 2026.Q2 looked like this:

addSiteSettings → addOrUpdateListTypeDefinitions → addOrUpdateUserGroups → addOrUpdateDataDefinitions → addOrUpdateObjectFolders → addOrUpdateDDMStructures → … → addStyleBookEntries → addOrUpdateRoles → addOrUpdateLayouts ← pages are created as EMPTY shells early → … addOrUpdateDocuments → addFragmentEntries → addObjectDefinitions → addOrUpdateObjectRelationships → addOrUpdateObjectFields → publishObjectDefinitions → addOrUpdateDDMTemplates → addOrUpdateObjectActions → addOrUpdateJournalArticles → addOrUpdateObjectEntries → addLayoutPageTemplates → addOrUpdateLayoutsContent ← page composition is applied LATE, once fragments, content, masters exist → addLayoutUtilityPageEntries → addSegmentsExperiences → addOrUpdateResourcePermissions

The pattern to rely on: things are created first and filled in later. Pages exist before their content so navigation menus and links can point at them; objects are created, related, given fields, and only then published; permissions come last so they can reference everything. For objects the chain is fixed: definitions → relationships → fields → publish → actions → entries.

Because publishing happens after creation, omit status from an object definition file — the initializer publishes it for you.

Applying a change

ChangeHow to apply itReprovision?
Theme / designDeploy the themeCSS CETNo
Object definition or dataobject-admin API, or edit the tree and reapplyNo
Fragment content, or a new fragmentEdit the source tree, then reprovisionYes
New page, page composition, fragment placementDelete the site, recreate from the initializerYes

Deploying a changed zip re-runs the initializer against the existing site (the PUT above). That upserts pages, objects, roles and similar keyed records, but in this project it did not reliably apply composition changes to pages that already exist, and fragment edits do not reach placed instances (the 2026.Q2 source does replace a content page’s composition on re-run, which can also wipe editor changes; see Pages). For those, delete the site and let the next deploy create it fresh — the reprovision cycle below.

The reprovision cycle

#!/usr/bin/env bash
set -o errexit -o nounset -o pipefail

SITE_ERC="${SITE_ERC:?}"      # e.g. badael-home-template
SITE_NAME="${SITE_NAME:?}"    # the "Initializing <name>" log string
CET="${CET:?}"                # the client-extensions/<CET> directory
PORT="${PORT:-8080}"
LOG=bundles/tomcat/logs/catalina.out

before=$(grep --count "Initializing ${SITE_NAME}" "${LOG}" || echo 0)

curl --output /dev/null --request DELETE --silent \
	--url "http://localhost:${PORT}/o/headless-admin-site/v1.0/sites/${SITE_ERC}" \
	--user "test@liferay.com:test"

rm -f "bundles/osgi/client-extensions/${CET}.zip"
(cd "client-extensions/${CET}" && blade gw clean deploy >/dev/null)

for _ in $(seq 1 100); do
	[[ $(grep --count "Initializing ${SITE_NAME}" "${LOG}" || echo 0) -gt ${before} ]] && break
	sleep 3
done

sleep 6   # handlers keep logging after the "Initializing" line

awk -v n=$((before + 1)) '/Initializing '"${SITE_NAME}"'/{c++} c>=n' "${LOG}" \
	| grep --extended-regexp 'Invoking|Initialized|InitializationException|MustNotBeReserved'
Two things go wrong when you do this by hand

1. before must be read before the delete. Read it late and you compare the new run against itself; the loop spins out on a build that actually succeeded.

2. The Initializing line is not the end of the run. Handlers keep logging after it, so sampling immediately shows a partial list and a missing handler reads as a failure. The run is over at Initialized <name> for group <id> in N ms — waiting for that line is more robust than a fixed sleep.

blade gw deploy with no source change rewrites nothing

Liferay re-triggers the initializer when the file-install watcher sees a changed zip, not when Gradle runs. Gradle's up-to-date check is content-based, so a redeploy with no edit prints BUILD SUCCESSFUL / "N up to date" and your site stays deleted. Hence the rm -f and clean above.

Sites are addressed by ERC in that DELETE path

A numeric site ID returns 404. Same rule across headless-admin-site — see Headless APIs.

Token substitution

Every file is passed through token replacement before it is parsed. Delimiters are [$ and $]. This is how a file references an entity whose numeric ID cannot be known when you write it.

TokenResolves to
[$GROUP_ID$], [$GROUP_KEY$], [$GROUP_FRIENDLY_URL$]Current site
[$COMPANY_ID$], [$PORTAL_URL$], [$PORTAL_PROPERTY:name$]Instance context
[$OBJECT_DEFINITION_ID:X$] / [$OBJECT_DEFINITION_CLASS_NAME:X$] / [$OBJECT_DEFINITION_PORTLET_ID:X$]Object ID / class name / its admin widget
[$LIST_TYPE_DEFINITION_ID:X$]Picklist ID
[$ROLE_ID:X$], [$LAYOUT_ID:/url$]Role / page
[$DOCUMENT_JSON:/path$], [$DOCUMENT_URL:name$], [$DOCUMENT_FILE_ENTRY_ID:…$]Document reference
[$JOURNAL_ARTICLE_ID:erc$], [$DDM_STRUCTURE_ID:X$], [$DDM_TEMPLATE_ID:X$]Content IDs
[$TAXONOMY_VOCABULARY_ID:X$], [$TAXONOMY_CATEGORY_ID:X$]Taxonomy IDs
[$ASSET_LIST_ENTRY_ID:X$], [$SEGMENTS_ENTRY_ID:X$], [$CLIENT_EXTENSION_ENTRY_ERC:X$]Collections, segments, CETs

Replacement is plain string substitution over the file, so a token whose key has a typo is not a parse error you can count on. The symptom tends to be a record pointing at nothing (a menu item with no page, a permission on no role) or a failed conversion further down. Check the resulting site, not just the log.

Object tokens are the exception — they see the whole company

Most tokens are registered by the handler that creates the entity, so they resolve only for entities in this tree. Object definitions are exempt: the handler runs a company-wide pass before reading any file, registering tokens for every published object definition in the company, whoever created it.

So a tree can freely reference objects created live over object-admin — resource-permissions.json, object-actions/, and object-relationships/ all resolve against them. Two conditions: the object must be published (drafts register nothing), and the token key is the definition's short name.

Do not generalise this. [$LIST_TYPE_DEFINITION_ID:X$] is registered inside the per-file loop, so it resolves for picklists in this tree only.

Verifying what actually happened

grep --extended-regexp 'Initializ|Invoking (addOrUpdateListTypeDefinitions|addObjectDefinitions|addOrUpdateObjectRelationships|addOrUpdateLayouts|addOrUpdateLayoutsContent|addLayoutPageTemplates|addStyleBookEntries|addFragmentEntries|addOrUpdateResourcePermissions)' \
	bundles/tomcat/logs/catalina.out | tail -20

The signal is the jump between runs, not the absolute number:

Invoking addStyleBookEntries took 1 ms      <- before: directory absent
Invoking addStyleBookEntries took 21 ms     <- after: files found
Invoking addLayoutPageTemplates took 0 ms   <- before: no master page
Invoking addLayoutPageTemplates took 134 ms <- after: master page imported
GotchaDetail
Fragments log as addFragmentEntriesNo addOrUpdate prefix. Grepping for addOrUpdateFragmentEntries matches nothing, which reads exactly like the directory was never found.
Navigation menus log nothingThat handler runs inside addOrUpdateLayoutsContent. Its absence proves nothing — count menu items over REST instead.
A flat timing is a hint, not a verdictSingle-file handlers can apply correctly and still round to 1 ms. Assert the outcome.
Log lines are not in folder orderSee the dependency graph above. Look for a handler by name, not by position.
Timestamps are UTCYour shell probably is not. A line that looks hours ahead may be the current run.

A failed initialization rolls the site back, so "the site does not exist" and "the initializer threw" are the same symptom. The failure is logged by BundleSiteInitializer at ERROR, sometimes with a message as unhelpful as null — read the stack trace underneath, and note which handler was the last one logged before it:

grep --extended-regexp 'InitializationException|MustNotBeReserved|Unable to transform|ERROR .*BundleSiteInitializer' \
	bundles/tomcat/logs/catalina.out | head

What the tree does and does not rebuild

Rebuilt from sourceNot rebuilt
Pages, fragments, masters, style books, menusThe themeCSS selection — manual, every time
Objects, picklists, relationships, actions, permissionsRuntime object entries (they survive instead, being company-scoped)
Roles and grantsAnything an admin changed in the UI and did not port back
Seeded web content and documentsEditor-authored content created after provisioning

Say plainly which half of the data layer your tree rebuilds. A mixed layout — objects managed live, their logic and permissions authored in the tree — is workable and common; it just needs to be stated rather than assumed.

Deleting the site does not delete company-scoped things

Object definitions, picklists, roles, users and company-scope documents live at the instance level. The reprovision cycle deletes the site; the next run finds those records and updates them by key. That is usually what you want, but do not assume that something you removed from the tree is removed from the instance — an upsert adds and updates; check before relying on deletion.

How it connects

  • Client extensions — the packaging

  • Fragments — fragments/group/
  • Objects — object-definitions/
  • Permissions — resource-permissions.json
  • Style books — what survives
  • Site templates — the alternative

Traps recap

No batch/ directory exists here

*.batch-engine-data.json files are packaged and silently ignored. The only signal is Invoking addOrUpdateListTypeDefinitions took 0 ms. That envelope belongs to the separate batch CET type.

Never copy "system": true

Portal-internal initializers (seo-studio, ai-hub) set it. Copied into your tree it makes the object or picklist non-modifiable.

The fragments nesting level is not optional

fragments/group/<collection>/fragments/<name>/. Drop the second fragments and the handler finds nothing, logs 1 ms, and the site provisions with no fragments — so every page that references one renders blank.

No theme, CSS or JS in the initializer project

A siteInitializer is a batch-classified CET, so it cannot share a project with themeCSS or globalJS (grouping rules). Put them in a sibling frontend project and deploy both.
