Pages & page types

Where everything else ends up. The page types that matter, several vocabularies for the word "type", and the composition tree that a page definition actually is.

In one sentence

A page is a URL in a site's navigation tree, with a type that decides how its body is produced — composed from fragments, filled with widgets, or pointed somewhere else entirely.

The page types

TypeWhat it isUse for
Content PageFragment-composed layout, edited in the page editor. The default.Everything, unless you have a specific reason not to
Collection PageA content page created already bound to a collectionIndex pages ("All news"); it is still a content page underneath
Widget PageLegacy portlet layout with column templatesOld portlet apps; compatibility only. Deprecated from 2026.Q3.
Page SetA node that groups child pages but is not itself a pageNavigation grouping ("About → …")
Link to a Page of This SiteA node that points at another pageShowing one page in two places in the menu
Link to URLA navigation node that redirectsExternal links inside the menu
EmbeddedAn iframe to an external URL, inside your chromeWrapping a third-party tool
Full Page Application / PanelOne widget filling the page / a menu of widgets shown one at a timeNothing new — both deprecated from 2026.Q3 with no automatic migration
Deprecations to plan around (as of 2026.Q2)

Private pages are deprecated since 2024.Q4 and disabled by default on new installations — design public pages plus permissions instead. In 2026.Q3 the Widget Page, Full Page Application, Panel and Widget Page Template types are deprecated behind feature flag LPD-76864 (off on new installs), and newer BundleSiteInitializer code already skips a widget page.json when that flag is off. On 2026.Q2 they still work, but nothing you build today should depend on them.

Pages that are not in the navigation tree

ThingWhat it isWhere it lives
Master pageThe chrome (header, footer) around a content page, with one drop zone for the page bodyDesign → Page Templates → Masters
Page templateA starting layout copied into a new page. Copied, not linked — later template edits do not reach existing pages.Design → Page Templates
Display page templateOne layout rendered for every item of a type, at the item's own URLDesign → Page Templates → Display Page Templates
Utility pageA content page for a system job: 404, 500, sign-in, create account, forgot password, cookie policyDesign → Utility Pages; layout-utility-page-entries/ in an initializer

All four are edited in the same page editor with the same fragments, which is why "a page" in Liferay conversations can mean any of them.

Several "type" vocabularies — do not mix them

The internal layout key is content/portlet/url/embedded/link_to_layout/node (page set)/utility. The headless-admin-site API enum is ContentPage/WidgetPage/LinkToURLPage/EmbeddedPage/PageSetPage/LinkToPagePage. A site initializer page.json takes Content/Portlet/URL/Embedded — lower-cased before use, with widget and link_to_layout accepted as aliases. And headless-delivery has its own pageType field. Copying a value from the wrong table is a 400 at best and a wrong page type at worst.

Public vs private, hidden vs visible

FlagMeaning
private: falseIn the public page set. Still needs a Guest VIEW grant to actually be public — see Permissions.
private: trueIn the private page set; requires site membership. Deprecated since 2024.Q4 and off by default on new installs — avoid.
hidden: trueReachable by URL, omitted from navigation. Used for display-page hosts and thank-you pages.

What a Content Page really is

A tree of page elements. Every content page has exactly one Root; everything else nests inside it.

Element typeRole
RootThe top of the tree
SectionA container: spacing, background, width (the editor's Container)
Row / ColumnGrid structure (the editor's Grid)
FragmentA fragment placement, by key + siteKey
WidgetA portlet embedded in a content page
CollectionA Collection Display, bound via collectionConfig
CollectionItemThe per-row template inside a Collection
DropZoneOn a master page: where the page's own body is injected
FragmentDropZoneThe contents of an lfr-drop-zone inside a fragment
FormA Form Container bound to an object definition
FormStepContainer / FormStep / FormRelationshipMulti-step forms and related-entry blocks inside a Form

That list is the complete PageElement.Type enum in headless-delivery (2026.Q2), which is what page-definition.json uses. headless-admin-site has a different enum for the same concepts (BasicFragment, Container, Grid, CollectionDisplay, FormContainer…) — yet another vocabulary.

Minimum viable page definition:

{
	"pageElement": { "pageElements": [], "type": "Root" },
	"version": "1.0"
}

Selecting a master and adding a fragment with a typed-in value:

{
	"pageElement": {
		"pageElements": [
			{
				"definition": {
					"fragment": { "key": "home-hero", "siteKey": "[$GROUP_KEY$]" },
					"fragmentFields": [
						{ "id": "hero-title", "value": { "text": { "value_i18n": { "en_US": "Welcome to Badael" } } } }
					]
				},
				"type": "Fragment"
			}
		],
		"type": "Root"
	},
	"settings": { "masterPage": { "key": "badael-master" } },
	"version": 1.1
}

fragmentFields[].id is the fragment's data-lfr-editable-id. Besides masterPage, the initializer reads themeName, colorSchemeName, css and themeSettings from settings — there is no key for a style book or a themeCSS client extension.

Drafts: why an edit is not live

Every content page has a hidden draft layout. The page editor writes to the draft; Publish copies it onto the live page. That is why an editor can work for an hour without visitors seeing anything, why "I changed it but nothing happened" usually means "I did not publish", and why the site initializer writes to the draft and then copies it across itself. With workflow enabled for content pages, Publish becomes a submission for review.

Page metadata (page.json)

{
	"friendlyURL": "/home",
	"hidden": false,
	"name": "Home",
	"name_i18n": { "en_US": "Home" },
	"permissions": [ { "actionIds": ["VIEW"], "roleName": "Guest", "scope": 4 } ],
	"private": false,
	"type": "Content"
}

scope: 4 is SCOPE_INDIVIDUAL — this page only. The scope table explains the other values, and why the wrong one silently grants nothing.

Navigation

Two independent things put links in a menu:

  1. The page hierarchy. The Classic theme's navbar renders non-hidden public pages on its own, whether or not you define a menu.
  2. Navigation menus. Explicit, ordered menus defined in site-navigation-menus.json, whose items are layout, url, node, or display-page.
[
	{
		"auto": false,
		"externalReferenceCode": "BADAEL_MAIN_MENU",
		"menuItems": [
			{ "externalReferenceCode": "NAV_HOME", "friendlyURL": "/home", "privateLayout": false, "type": "layout" }
		],
		"name": "Main Menu",
		"typeSite": 1
	}
]
A bad friendly URL is skipped, not reported

A layout menu item is resolved by friendly URL. No match logs "No layout found with friendly URL /whatever" and the item is dropped — the menu still provisions, just shorter. Count items over REST after provisioning rather than trusting the build.

Creating pages via API

POST /o/headless-admin-site/v1.0/sites/{siteExternalReferenceCode}/site-pages
ERC, not numeric ID

headless-admin-site keys sites by external reference code in the path. A numeric site ID returns 404 — which reads as "the endpoint does not exist" and sends people hunting for a feature flag. (headless-admin-content and headless-delivery, confusingly, do use numeric siteId.)

Feature flags gate the page APIs

Defaults in 2026.Q2 portal.properties: LPD-35443 (beta, off) for public layouts, LPD-39244 (off) for fragment/page composition, LPD-74328 (off) for page-element creation; LPD-38869 is a deprecation-type flag that defaults to on. A 404 from a page endpoint usually means a flag, not a typo. Turn them on in Instance/System Settings → Feature Flags, or with feature.flag.LPD-35443=true in portal-ext.properties.

Traps

Page composition changes need a full reprovision

Deploying a changed site initializer re-runs it against the existing site, but don't count on that to update a page that already exists. In this project, edits to an existing page's page-definition.json reliably showed up only after the site was deleted and recreated, so that is the verified path. Be aware that the 2026.Q2 BundleSiteInitializer source does replace a content page's stored composition when it runs, deleting and re-importing its fragment instances. So a re-run can also wipe editor changes on that page. Either way, treat initializer-owned pages as code, not as something editors maintain.

Changing a page's type deletes and recreates it

If page.json's type no longer matches the existing page at that friendly URL, BundleSiteInitializer deletes the old page and adds a new one — new plid, new permissions, editor content gone. Decide the type once.

Deleting the site does not delete your objects

Object definitions and entries are company-scoped and survive site deletion — so reprovisioning is safe for runtime data. The exception is an object explicitly scoped to the site; those entries go with it.
