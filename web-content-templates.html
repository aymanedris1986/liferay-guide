Web Content Templates

FreeMarker markup that turns a structure's field values into HTML. Server-side, cached, and swappable without touching a single article.

In one sentence

A Web Content Template is a FreeMarker script attached to a Content Structure. It receives the field values of one article and outputs HTML.

What it actually is

Liferay hands your template one variable per structure field. You write ordinary HTML with FreeMarker directives around it. The output is rendered on the server and, by default, cached. There's no JavaScript and no client round-trip, and it works for search engines and for visitors with JS disabled.

You create them in Site Menu → Content & Data → Web Content → Templates. In a site initializer each one is a folder under ddm-templates/ holding a ddm-template.json (ddmTemplateKey, ddmStructureKey, name) and the script itself as ddm-template.ftl.

<article class="news-card">
	<h3>${headline.getData()}</h3>

	<#if (summary.getData())?has_content>
		<p>${summary.getData()}</p>
	</#if>

	<#if (heroImage.getData())?has_content>
		<img alt="${heroImage.getAttribute("alt")}" data-fileentryid="${heroImage.getAttribute("fileEntryId")}" src="${heroImage.getData()}">
	</#if>
</article>

Repeatable fields and field sets turn into lists you can iterate. Inside a repeatable field set, you reach each child field through the current repetition:

<ul>
	<#list links.getSiblings() as link>
		<li><a href="${link.url.getData()}">${link.label.getData()}</a></li>
	</#list>
</ul>

The variable name is the Field Reference, not the label

Since 7.4, every structure field has a Field Reference, which you can see in the field's advanced settings. If you don't set one, Liferay generates it, e.g. Text84729103. The Field Reference is the FreeMarker variable name. It is also the field-reference/name attribute in the article XML and the name in the Headless contentFields payload. Set a readable reference (headline, heroImage) before you write templates or load content. Renaming it later breaks every template and every stored value that uses the old name.

The template editor's left panel lists every field of the bound structure. Clicking one inserts the code Liferay generates for that field type. Use that as your starting point for Image, Date and Link-to-Page fields, which are not plain strings:

<#assign publishDate_Data = getterUtil.getString(publishDate.getData())>
<#if validator.isNotNull(publishDate_Data)>
	<#assign publishDate_DateObj = dateUtil.parseDate("yyyy-MM-dd", publishDate_Data, locale)>
	${dateUtil.getDate(publishDate_DateObj, "dd MMM yyyy", locale)}
</#if>

Generic templates and embedding

You can create a template with no structure. It can't render an article by itself, but other templates can pull it in. Use this for shared macros (a date formatter, a share-bar):

<#include "${templatesPath}/BADAEL-MACROS" />   <#-- the generic template's key -->

The template family: don't confuse these

FreeMarker shows up in several places that look alike but have different scopes:

KindRendersAttached to
Web Content TemplateOne article's fieldsA Content Structure
Information TemplateOne item of any info-framework type: web content, document, blog, category, object entryAn item type (+ subtype). Can only be used by mapping a fragment field, not in widgets
Widget Template (formerly ADT)A widget's list output: Asset Publisher, Documents, Categories Navigation, BreadcrumbA widget type
Fragment (FreeMarker)A page building blockA fragment, with configuration.* in scope
Notification templateAn email or notification bodyA notification. Uses [%TERM%] tokens by default. FreeMarker is an optional editor type

All of these, plus the page-layout ones, are laid out side by side on All template types.

When to use a template vs a fragment

Use a Web Content Template whenUse a Fragment when
The markup belongs to the content type: every news article should look like this everywhereThe markup belongs to the page: this hero looks like this on this layout
You need loops and conditionals over repeatable fieldsYou want editors to drag, drop, configure, and edit in place
The output is reused by widgets and display pages alikeYou need per-placement configuration options
You want zero page-editor involvementYou want the page editor to own the composition
They compose

The usual pattern uses both. A Collection Display fragment renders the list, and each item is rendered by the structure's card template. The fragment owns the grid; the template owns the card.

Where Web Content is heading

As of DXP 2026.Q1, Liferay lists classic Web Content as being in maintenance mode. It points new work to the new object-based Liferay CMS, which is behind the CMS feature flag in 2026.Q2 and GA from 2026.Q3. Existing structures and templates keep working. For a new, non-journal content type, consider an Information Template or a fragment instead. They work for any item type, while a Web Content Template only ever renders journal articles.

Traps

serviceLocator is restricted by default

By default, serviceLocator is on the FreeMarker engine's Restricted Variables list, along with objectUtil, staticFieldGetter, staticUtil and a few others. The setting is in Control Panel → System Settings → Template Engines → FreeMarker Engine. Removing it lets anyone who can edit a template call any service. That is the same class of risk as Groovy object actions. Use restClient (which respects the viewer's permissions) or a CET, and design for serviceLocator being off.

A missing field throws, it does not blank

If a template references a variable the structure doesn't define, FreeMarker raises an error and the whole block fails to render. ?has_content on (x.getData()) only guards an empty value. To survive a field that might not exist, use x?? or the ! default operator: (summary.getData())!"". After any structure change, re-check every template bound to it.

Cacheable + per-user output = wrong content for everyone

New templates are Cacheable by default, so the rendered HTML is reused. If the template depends on the request, the current user, taglibs, or restClient results, turn Cacheable off. Otherwise the first visitor's rendering is what everyone else sees. The Liferay docs name taglibs, request handling and API queries as the reasons to turn it off. In the current site-initializer code path, templates are created with Cacheable off. If you want caching, check the setting after provisioning.

Templates are per-structure, and that binding is by key

Both the structure and the template are referenced by key (ddmStructureKey, ddmTemplateKey) in initializer files and API payloads. Renaming the display name is safe; changing the key breaks the link with no error at build time. Once a template is saved against a structure, you can't re-point it to another structure.

Escaping

${field.getData()} on a Rich Text field emits raw HTML by design. On a Text field that an editor controls, the same thing is an injection surface. Use ${htmlUtil.escape(field.getData())} (or FreeMarker's ?html) when the value should be treated as text. Escape attribute values like alt the same way.
