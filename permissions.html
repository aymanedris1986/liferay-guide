Roles & permissions

Who can see and do what. Almost every "it works for me but not for them" bug on a Liferay project is on this page.

The model in one diagram

USER ──belongs to──▶ SITE / ORGANIZATION / USER GROUP / ACCOUNT │ │ └──────assigned──────▶ ROLE ──────grants──────▶ ACTION on RESOURCE at SCOPE │ (VIEW, UPDATE, ADD_ENTRY…) ┌───────────────┼───────────────┐ Regular role Site role Organization role (portal-wide) (per site) (per org)
Role typeAppliesUse for
RegularEverywhere in the instanceAdministrator, HR Manager (global)
SiteWithin one siteSite Content Editor, Site Member
OrganizationWithin one org and optionally its childrenDepartment Head
AccountWithin a B2B accountCommerce buyer, account admin

Two roles exist that you never assign: Guest (anyone not signed in) and User (anyone signed in). Guest is where the interesting failures live.

Guest access — the failure mode

Everything on this page fails silently

The page returns 200, the entry saves, nothing appears in the log, and it all looks correct to you — because your session has the access the visitor lacks. These are not error-handling problems; they are "the list is empty and nobody knows why" problems.

Gate 1: the Service Access Policy

Permissions are the second gate. The first is the Service Access Policy (SAP), which decides whether a Headless endpoint is reachable at all — before any permission is consulted. A public fragment fetching web content fails here while every grant you are staring at is correct.

A policy is a named set of allowed service signatures — the implementation method, not the REST path:

com.liferay.headless.delivery.internal.resource.v1_0.StructuredContentResourceImpl#getStructuredContent
com.liferay.headless.delivery.internal.resource.v1_0.NavigationMenuResourceImpl#getNavigationMenu

Author it at Control Panel → Security → Service Access Policy, in Advanced Mode (the basic form does not expose raw signatures). Two booleans must both be right:

FieldSet toWhy
DefaultcheckedA policy applies to unauthenticated requests only when marked default. Liferay unions the company's default entries on every request; a non-default policy is active only when something names it explicitly.
EnabledcheckedA disabled entry is skipped entirely.

Resolve a signature by finding the resource class behind the endpoint — the internal.resource.v1_0 package of the module in the Headless API table.

Necessary but not sufficient. A policy makes the endpoint reachable; the resource still has to be readable. Both gates, or the visitor gets an empty result that looks like missing data.

Gate 2: the VIEW grant

Publishing an object does not make its entries readable. Page-level VIEW does not confer entry-level VIEW, and a server-side Collection does not sidestep it — it evaluates entry permissions as the visiting user, so an object-backed listing renders empty for Guest while looking right to you.

An object has two resources

The action decides which resource name to grant on. Getting this wrong applies cleanly and grants nothing.

ResourceActionsGuest may hold
com.liferay.object.model.ObjectEntry#<id> — what [$OBJECT_DEFINITION_CLASS_NAME:X$] resolves toVIEW, UPDATE, DELETE, PERMISSIONSVIEW
com.liferay.object#<id> — written com.liferay.object#[$OBJECT_DEFINITION_ID:X$]ADD_OBJECT_ENTRY, PERMISSIONSADD_OBJECT_ENTRY

UPDATE, DELETE and PERMISSIONS are guest-unsupported — ungrantable to Guest at any scope.

Granting in source: resource-permissions.json

[
	{
		"actionIds": ["VIEW"],
		"primKey": "0",
		"resourceName": "[$OBJECT_DEFINITION_CLASS_NAME:Policy$]",
		"roleName": "Guest",
		"scope": "1"
	}
]
scope is the trap

It is a ResourceConstants integer, and the wrong value fails silently — the handler reports no error and grants nothing useful.

scopeConstantGrants
"1"SCOPE_COMPANYAll existing and future entries. This is the one that makes a public listing work.
"2"SCOPE_GROUPThe same, limited to the current site
"3"SCOPE_GROUP_TEMPLATEOnly the defaults applied to newly created entries. Does nothing for existing ones.
"4"SCOPE_INDIVIDUALOne entry, named by primKey. Used by page permissions.

Several Liferay-internal initializers use "3", so it gets copied. For scopes 1 and 2 the handler overwrites primKey with the company or group ID, so "0" is a fine placeholder.

The handler warns rather than fails

A bad resourceName or unknown roleName logs "No resource action found" / "No role found" and carries on. A silent 2 ms run with no warning means the grant applied as written — so if behaviour did not change, suspect scope, not the syntax.

Per-entry permissions

Object entries can be permissioned individually via the collaborators API — "only the requester and their manager can see this leave request". Requires feature flag LPD-17564.

How to verify — as the visitor, not as you

# curl with no --user and no cookie jar IS a Guest request
curl --silent --url "http://localhost:8080/web/badael/home" > /tmp/page.html

# assert real values are present AND placeholder strings are absent
grep -c "Annual Leave Policy" /tmp/page.html
grep -c "{{" /tmp/page.html

Placeholders still present mean the data did not resolve. Then open it signed out in a browser: curl executes no JavaScript, so anything client-side is unverified until you do.

How it connects

  • Objects — two resources, two grants
  • Collections — why the list is empty
  • Forms — write-only public objects
  • Pages — page-level VIEW
  • Site initializers — where grants live in source
  • Headless APIs — what SAP gates
  • CETs — OAuth scopes are a separate gate again

The three independent gates, in order

request ──▶ [1] Service Access Policy reachable? no ──▶ 403 / nothing │ yes [2] OAuth scope (token calls only) no ──▶ 403 │ yes [3] Permission grant on the resource no ──▶ 200 with an EMPTY list │ yes data

Note the asymmetry that costs the most time: gates 1 and 2 return an error you can see. Gate 3 returns success with nothing in it.
