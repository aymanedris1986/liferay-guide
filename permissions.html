Roles & permissions

Who can see and do what. Almost every "it works for me but not for them" bug on a Liferay project is on this page.

The model in one diagram

USER ──belongs to──▶ SITE / ORGANIZATION / USER GROUP / ACCOUNT │ │ └──────assigned──────▶ ROLE ──────grants──────▶ ACTION on RESOURCE at SCOPE │ (VIEW, UPDATE, ADD_ENTRY…) ┌──────────┬──────────┼───────────┬──────────────┐ Regular Site Organization Account Asset library (instance) (a site) (an org) (an account) (a library)
Role typeAppliesUse for
RegularEverywhere in the instanceAdministrator, HR Manager (global), anything cross-site
SiteWithin the site(s) where the user was given itSite Content Reviewer, Site Administrator
OrganizationWithin the organization the user was given it for, and that organization's siteDepartment Head, Organization Administrator
AccountWithin one account (B2B/B2C)Buyer, Account Administrator; and account-restricted object entries
Asset libraryWithin one asset library (called depot in code and workflow XML)Asset Library Content Reviewer

There is also a Publications role type, used only by the Publications (change-list) feature. The type is chosen when you create the role and cannot change: a regular role cannot be "given in one site", and a site role grants nothing outside the sites where it is assigned. That is the most common reason a role "does not work": right permissions, wrong type.

The implicit roles

Some roles are never assigned by hand; Liferay decides membership at runtime:

RoleWho has itWhy it matters
GuestAnyone not signed in — and, by default, everyone signed in tooSee the callout below
UserEvery signed-in user"Any authenticated user" grants, instance-wide
Site MemberMembers of the current siteA site role; "our intranet's staff" grants go here, not on User
Organization UserMembers of the current organizationThe organization equivalent of Site Member
OwnerThe creator of the specific item being checkedWhy authors can see and edit their own entries — and why testing as the author proves nothing
Signed-in users inherit Guest

permissions.check.guest.enabled=true (the default in portal.properties) makes permission checks assume every user also has the Guest role. So a Guest VIEW grant is effectively a grant to everyone, and you never need to repeat it on User. The reverse is not true: a Site Member grant does nothing for visitors. Guest is where the interesting failures live.

Resources, actions and where a grant is stored

Every permissionable thing is a resource with a fixed list of actions, declared in the module's resource-actions XML. There are three kinds:

KindExampleTypical actions
Portlet (application)The Web Content admin app, an object's admin appACCESS_IN_CONTROL_PANEL, ADD_TO_PAGE, CONFIGURATION
Root model ("the app's data as a whole")com.liferay.journal, com.liferay.object#<id>ADD_ARTICLE, ADD_OBJECT_ENTRY, PERMISSIONS
Model (one item)A web content article, an object entry, a pageVIEW, UPDATE, DELETE, PERMISSIONS

A grant is a row saying "role R may do action A on resource N at scope S" — the scope is covered below. The XML also declares defaults (what Guest, Site Member and Owner get on each new item) and guest-unsupported actions, which the UI and API refuse to grant to Guest at all.

Guest access — the failure mode

Everything on this page fails silently

The page returns 200, the entry saves, nothing appears in the log, and it all looks correct to you — because your session has the access the visitor lacks. These are not error-handling problems; they are "the list is empty and nobody knows why" problems.

Gate 1: the Service Access Policy

Permissions are the second gate. The first is the Service Access Policy (SAP), which decides whether a Headless endpoint is reachable at all — before any permission is consulted. A public fragment fetching web content fails here while every grant you are staring at is correct.

A policy is a named set of allowed service signatures — the implementation method, not the REST path:

com.liferay.headless.delivery.internal.resource.v1_0.StructuredContentResourceImpl#getStructuredContent
com.liferay.headless.delivery.internal.resource.v1_0.NavigationMenuResourceImpl#getNavigationMenu

Author it at Control Panel → Security → Service Access Policy, in Advanced Mode (the basic form does not expose raw signatures). Two booleans must both be right:

FieldSet toWhy
DefaultcheckedA policy applies to unauthenticated requests only when marked default. Liferay unions the company's default entries on every request; a non-default policy is active only when something names it explicitly.
EnabledcheckedA disabled entry is skipped entirely.

Resolve a signature by finding the resource class behind the endpoint — the internal.resource.v1_0 package of the module in the Headless API table.

Necessary but not sufficient. A policy makes the endpoint reachable; the resource still has to be readable. Both gates, or the visitor gets an empty result that looks like missing data.

Gate 2: the VIEW grant

Publishing an object does not make its entries readable. Page-level VIEW does not confer entry-level VIEW, and a server-side Collection does not sidestep it — it evaluates entry permissions as the visiting user, so an object-backed listing renders empty for Guest while looking right to you.

An object has two resources

The action decides which resource name to grant on. Getting this wrong applies cleanly and grants nothing.

ResourceActionsGuest may hold
com.liferay.object.model.ObjectDefinition#<id> — the entry model; what [$OBJECT_DEFINITION_CLASS_NAME:X$] resolves toVIEW, UPDATE, DELETE, PERMISSIONS (plus extras such as OBJECT_ENTRY_HISTORY when enabled)VIEW
com.liferay.object#<id> — the root resource; written com.liferay.object#[$OBJECT_DEFINITION_ID:X$]ADD_OBJECT_ENTRY, PERMISSIONSADD_OBJECT_ENTRY

Yes, the entry resource is named after ObjectDefinition: every custom object's class name is com.liferay.object.model.ObjectDefinition# plus the definition id. UPDATE, DELETE and PERMISSIONS are guest-unsupported — ungrantable to Guest at any scope.

New objects have no defaults at all

The resource-actions template Liferay generates for every custom object has empty guest-defaults and empty site-member-defaults. Web content, by contrast, gives Guest VIEW on new articles by default. So the habit "content is public unless I restrict it" is exactly backwards for objects: entries are private to their owner and admins until you grant VIEW.

Granting in source: resource-permissions.json

[
	{
		"actionIds": ["VIEW"],
		"primKey": "0",
		"resourceName": "[$OBJECT_DEFINITION_CLASS_NAME:Policy$]",
		"roleName": "Guest",
		"scope": "1"
	}
]
scope is the trap

It is a ResourceConstants integer, and the wrong value fails silently — the handler reports no error and grants nothing useful.

scopeConstantGrants
"1"SCOPE_COMPANYAll existing and future entries. This is the one that makes a public listing work.
"2"SCOPE_GROUPThe same, limited to the current site
"3"SCOPE_GROUP_TEMPLATEOnly the defaults applied to newly created entries. Does nothing for existing ones.
"4"SCOPE_INDIVIDUALOne entry, named by primKey. Used by page permissions.

Several Liferay-internal initializers use "3", so it gets copied. For scopes 1 and 2 the handler overwrites primKey with the company or group ID, so "0" is a fine placeholder.

The handler warns rather than fails

A bad resourceName or unknown roleName logs "No resource action found" / "No role found" and carries on. A silent 2 ms run with no warning means the grant applied as written — so if behaviour did not change, suspect scope, not the syntax.

Inheritance: less than you expect

Liferay permissions are not a file-system ACL. Almost nothing flows down automatically:

  • Grants do not propagate. Setting permissions on a folder does not rewrite the permissions of the documents in it (permissions.propagation.enabled=false by default). Existing items keep what they had.
  • VIEW is checked up the tree. With permissions.view.dynamic.inheritance=true (the default), seeing a document also requires VIEW on its folder and every parent folder; the same for categories. So one restricted folder hides everything below it, whatever the items themselves say.
  • New items copy defaults once. Defaults from the resource-actions XML (or the "Permissions" section of the create form) are copied onto the item when it is created. Changing defaults later does not touch existing items — which is why the company-scope grant below exists.
  • Page VIEW does not imply content VIEW. A visitor can open a public page and see an empty list because they cannot VIEW the entries on it.

Per-entry permissions

Individual object entries can carry their own grants, like any model resource, through the entry's Permissions action in the admin app or over REST at /o/c/<plural>/{id}/permissions. For "only the requester and their manager can see this leave request" there are three routes, in order of preference:

  1. Don't grant VIEW broadly and rely on Owner: the requester sees their own entries, a role such as HR sees all.
  2. Account restriction: relate the object to Account and restrict it, so entries are visible only inside their account.
  3. The collaborators API (/o/c/<plural>/{id}/collaborators, built on the Sharing framework) to share one entry with named users. It is gated by feature flag LPD-17564, whose title in 2026.Q2 is "CMS" (the new headless CMS) and which depends on LPD-34594 (Root Object Definitions). Both are off by default — treat this as preview.

How to verify — as the visitor, not as you

# curl with no --user and no cookie jar IS a Guest request
curl --silent --url "http://localhost:8080/web/badael/home" > /tmp/page.html

# assert real values are present AND placeholder strings are absent
grep -c "Annual Leave Policy" /tmp/page.html
grep -c "{{" /tmp/page.html

Placeholders still present mean the data did not resolve. Then open it signed out in a browser: curl executes no JavaScript, so anything client-side is unverified until you do.

The three independent gates, in order

request ──▶ [1] Service Access Policy reachable? no ──▶ 403 / nothing │ yes [2] OAuth scope (token calls only) no ──▶ 403 │ yes [3] Permission grant on the resource no ──▶ 200 with an EMPTY list │ yes data

Note the asymmetry that costs the most time: gates 1 and 2 return an error you can see. Gate 3 returns success with nothing in it.
