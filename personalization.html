Segments & experiences

Showing different content to different people, on the same URL. Segments define who; experiences define what they see; A/B testing decides which wins.

The three pieces

SEGMENT "Managers" · "Arabic speakers" · "New joiners (< 90 days)" │ who the visitor is ▼ EXPERIENCE a whole alternative composition of ONE page, bound to a segment │ what they see ▼ A/B TEST two variants of an experience, measured against a goal which one performs better
2026.Q1 changed where segments are authored

From 2026.Q1, local segment authoring in DXP is deprecated: segmentation is moving to Analytics Cloud as the single source of truth. On a new installation the Segments app is read-only by default and shows segments synced from Analytics Cloud; to create or edit segments locally you enable the deprecation feature flag LPD-78863, which will be removed in a future release. Upgraded installations keep local authoring for at least a year, with a deprecation badge. So on a fresh 2026.Q2 environment, "I cannot create a segment" is a flag, not a permission problem — and anything you build on locally-defined segments has a clock on it.

Segments

A segment is a saved audience definition, evaluated per request. Criteria come from four property groups in the segment editor:

GroupExamples
UserEmail, name, job title, screen name, date of birth, regular role, site, team, user group, tags
OrganizationName, type, parent organization, hierarchy path, country, region, tags
SessionBrowser, device, language, signed-in state, last sign-in, local date, URL, referrer URL, request parameters, cookies, IP-geocoded country
SegmentsOther segments, combined into a compound segment

Behavioural audiences — "viewed three pricing pages", "came from the spring campaign" — are built in Analytics Cloud and synced into DXP; the DXP editor itself only sees the request and the user record.

Segments are reusable: define "Managers" once and use it for page experiences, collection variations, and A/B tests.

Segments in an initializer

BundleSiteInitializer has handlers for both halves. segments-entries.json is an array of segments, upserted by segmentsEntryKey:

[
	{
		"active": true,
		"criteria": { … the criteria JSON the segment editor stores … },
		"name_i18n": { "en_US": "Managers" },
		"segmentsEntryKey": "BADAEL_MANAGERS"
	}
]

Each segment publishes [$SEGMENTS_ENTRY_ID:BADAEL_MANAGERS$], [$SEGMENTS_ENTRY_ERC:…$] and [$SEGMENTS_ENTRY_SCOPE_ERC:…$] tokens. Do not hand-write criteria: build the segment once in the UI (with the flag above if needed) and copy its stored criteria.

Experiences come from segments-experiences/<name>/segments-experiences.json, which names the page and the segment, with the experience's own composition in a sub-directory beside it:

segments-experiences/managers-home/ ├── segments-experiences.json │ { "friendlyURL": "/home", │ "name_i18n": { "en_US": "Managers" }, │ "segmentsEntryERC": "[$SEGMENTS_ENTRY_ERC:BADAEL_MANAGERS$]", │ "segmentsEntryScopeERC": "[$SEGMENTS_ENTRY_SCOPE_ERC:BADAEL_MANAGERS$]", │ "active": true } └── home/ ├── page.json "type": "Content" └── page-definition.json the experience's own composition
The experience handler has sharp edges

It looks the page up among public pages only; it appends a new experience each time it runs rather than upserting one; and if any segments-experiences/*/ folder lacks its segments-experiences.json, the handler returns — skipping every folder after it, in no guaranteed order. One folder per experience, always with its JSON.

Segment vs role — they are not the same thing

A role answers "what may this person do" and is enforced by the security layer. A segment answers "what should this person see" and is a presentation concern. Never use a segment to hide sensitive content — the content is still served, just not shown. Use permissions for that.

Experiences

An experience is a complete alternative composition of one content page, bound to a segment. Same URL, same page, different fragments, different mapped content, different collections. Technically, each experience is its own copy of the page's layout structure and its own set of fragment instances, keyed by experience ID — which is exactly why they do not share edits.

PropertyBehaviour
PriorityExperiences are ordered; the highest-ranked one whose segment matches wins. Reorder with the up/down controls in the experience menu.
DefaultThe fallback, matching everybody. Always exists.
CreationA new experience starts as a copy of Default and targets the Anyone segment until you change it
ScopePer page. Not per site, not per fragment.
EditingEach experience is edited independently in the page editor
Experiences multiply your maintenance

Three experiences on a page means three compositions to update when the design changes. A new experience is copied from Default once, then never hears from it again — no inheritance. Use them where the difference is genuinely worth it — a different hero and CTA — not to vary a single word.

Cheaper alternatives to a full experience

NeedCheaper option
One list differs by audienceA personalized collection variation per segment — one page, one display
One block differs by audienceA collection filtered by a category the audience already implies
Language differencesLocalisation, not segmentation — Web Content is translatable per field
Signed-in vs signed-outPage permissions plus a separate page, usually clearer
Department-specific newsOne page, one collection, filtered by the user's department category

Element variations (beta)

Behind feature flag LPD-85746 (the same flag as Audiences), variations can target a single element instead of the whole page — replace its inner HTML, run JavaScript, or hide it. They are applied in the browser, after the server has rendered the experience. That makes them cheap to maintain, and also means the original markup was sent to the visitor: fine for a different CTA, never for anything confidential. Beta — do not build a delivery on it.

A/B testing

With Analytics Cloud connected, an A/B test runs variants of one experience against a goal (such as clicks or bounce rate) and reports a winner, which you can then publish. While a test is running the experience under test is read-only, so editors cannot skew the result mid-test.

  • Needs enough traffic to reach significance — on an intranet with 300 users, usually it does not.
  • Requires Analytics Cloud; without it you get experiences but no measurement.
  • Test one meaningful change at a time; two changes give you an unattributable result.

How it connects

  • Pages — experiences are per page
  • Fragments — what varies
  • Collections — often the cheaper variation
  • Categories — audience-aligned content filtering
  • Permissions — for anything that must be hidden, not just unshown
  • Objects — user attributes segments read

Traps

Segmentation is not security

Content excluded by a segment is still on the server and still permitted. Anyone who can guess a URL or read an API response gets it. If it must not be seen, it needs a permission.

Caching interacts with personalisation

Personalised pages cannot be cached as aggressively as static ones. A page with many experiences is a page you are serving fresh each time — worth knowing before applying it to the homepage.

Experiences from source arrive at site creation only

The segments-experiences/ handler runs with the rest of the initializer, at site creation. Like any page composition change, adding an experience to an existing page needs a reprovision to come from source — and given the append behaviour above, re-running the handler against a live site would duplicate experiences rather than update them.
